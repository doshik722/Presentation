# GRPO: параметры реализации и описание для статьи

Решения 07–08.11.2026, старт с исходной T-lite — 13.11.2026; сравнение алгоритмов согласовано с научным руководителем. Решения и их история — `decisions.md`, раздел 9; разборы тонких мест — `subtleties.md`, раздел
«Обучение с подкреплением»; источники — `references.md`.

Версия: GRPO, μ = 1. PPO описывается отдельно при переходе к нему; общая часть (данные, генерация, награда, модель,
оптимизатор, validation, журнал, проверки) у двух алгоритмов одинаковая.

Статус: **принято** — согласовано; **по пилоту** — значение фиксируется пилотом до основных запусков и пишется
в манифест; **открыто** — ещё обсуждается.

## Часть 1. Параметры и обоснование

### 1. Термины этой схемы

- **Задание** — тема в одном из двух режимов («Поиск: есть» / «Поиск: нет»).
- **Эпизод** — один ответ на одно задание: запрос → (вызовы поиска и выдача) → презентация.
- **Группа** — 8 эпизодов на одно задание; внутри неё ответы сравниваются между собой.
- **Шаг** — 8 групп (64 эпизода) и одно обновление весов.
- **Чекпоинт** — сохранённый адаптер; каждые 10 шагов.

### 2. Данные и шаг

| Параметр | Значение | Обоснование |
|---|---|---|
| Задания | 274 темы train × 2 режима = 548 | Модель должна уметь и искать, и писать без поиска; одна модель учится обоим режимам сразу |
| Группа G | 8 ответов на задание | Среднее группы — база вместо критика; при 8 ответах оно уже устойчиво, генерация посильна |
| Заданий на шаг | 8: 4 с поиском + 4 без; режим общий для группы | Каждый шаг учит обоим режимам; ответы одной группы сравниваются в одинаковых условиях |
| Эпизодов на шаг | 64 | Это 8 независимых тем, а не 64 наблюдения: ответы группы связаны темой |
| Эпоха по заданиям | 68 полных шагов + 1 неполный (2 + 2 задания, 32 эпизода) | 548 / 8 = 68,5; все формулы — по фактическому числу эпизодов шага |
| Порядок заданий | две очереди (по режимам), перемешиваются по сиду, без повторов внутри эпохи | Равномерный охват тем, воспроизводимость |
| Предел | 150 шагов сбора (≈ 2,2 эпохи) = 9536 обучающих эпизодов (шаги 69 и 138 неполные: 148 × 64 + 2 × 32) | Один проход (68 шагов) для RL мало, а тем всего 274. Задание встречается ~2 раза, но каждый раз ответы новые — от обновлённой модели (это не μ = 2). Окончательно — после пилота по времени шага |

Шаги сбора и успешные обновления считаются раздельно (GradScaler может пропустить обновление); пропусков > 5% — разбор.
Абляции (16 заданий × 4 ответа, адаптивный β и др.) отложены. **Принято.**

### 3. Эпизод

| Параметр | Значение | Обоснование |
|---|---|---|
| Новых токенов модели | ≤ 12 000 на эпизод (до 13.11.2026 — 8000) | Просьбы о 25–30 слайдах (≈ 8,3–10 тыс. токенов) выполнимы; меняется только между запусками (`decisions.md`, раздел 9) |
| Реплик модели | ≤ 12 | Лимит вызовов + 2 |
| Вызовов инструментов | ≤ 10; неразобранный вызов и повтор тоже расходуют лимит | Иначе модель могла бы бесконечно повторять отклонённые вызовы |
| Повтор: среда | точное совпадение (тот же инструмент, аргумент после strip) — не выполняется, ответ «Такой запрос уже был» | Почти не тратит контекст |
| Повтор: награда | критерий `rewards.py` (search — тот же набор лемм запроса; open/read — тот же id), −0,1 | Перефразировка другими словами повтором не считается |
| Чтение | до 6000 знаков за вызов | Раздел статьи, не вся статья |
| Предел контекста | 25 000 токенов (проверка памяти: пик 30,3 ГБ из 31,7 при 12 000 токенов модели) | Без общего предела 10 чтений + промпт + 12 000 токенов модели дают до 20–25 тыс. Выдача обрезается под остаток; при исчерпании эпизод заканчивается «по длине» |
| Незаконченный ответ | разбирается как есть, оценивается наградой | Битые строки штрафует формат, недостающие слайды — покрытие |

«Прочитанный текст» (для проверки цитат и аналитики) — только выдача, фактически показанная модели после всех
обрезаний; берётся из токенов эпизода, а не из кеша. **Принято.**

### 6. Преимущество

A_i = sg[(r_i − среднее группы) / max(std шага, 0,02)]; float32, std с `correction=0`, по фактическим эпизодам шага.

- **Среднее группы** убирает уровень задания (лёгкая или трудная тема) и заменяет критик. Штраф относительный:
  ответ с наградой ниже среднего своей группы получает A < 0, даже если награда положительная.
- **Разброс всего шага, а не группы**: деление на разброс своей группы (исходный GRPO) растягивает группу почти равных
  ответов до размера группы с явным победителем — шум выдаётся за сигнал. Один делитель на шаг сохраняет соотношение
  групп и делает размер шага обучения независимым от масштаба награды (Lite PPO).
- **Нижняя граница 0,02** (≈ 24% σ = 0,084) — сигнал не раздувается, если почти все ответы шага одинаковы.
- Группы с низким разбросом **не выбрасываются** (награда непрерывная, точные ничьи почти невозможны, выброс убрал бы
  и KL). В журнал — доля групп с std < 0,02 и отдельно точные ничьи.

### 7. Функция потерь

L = (1/N) · Σ_{i,t} m_{i,t} · [ −sg(A_i) · ρ_{i,t} + (β/2) · (log π_θ − sg(log π_ref))² ]

| Элемент | Значение | Обоснование |
|---|---|---|
| μ (обновлений на пакет) | 1 | Настройка экспериментов DeepSeekMath; данные строго свои (on-policy). μ > 1 — повтор тех же ответов; при малом lr почти равносилен увеличению lr |
| ρ | exp(log p − sg(log p)) | Значение 1, градиент ∇log p (константа 1 дала бы нулевой градиент). Значение ρ не доказывает on-policy — это проверяется отдельно (раздел 4) |
| Клиппинг | ε = 0,2 в общем коде; при μ = 1 не срабатывает | Ограничивает уход от политики сбора при повторных проходах; при одном обновлении уйти некуда — в тексте так и пишем |
| log p | `log_softmax(logits.float() / T)` у политики и опорной | Вероятности из того же распределения, что при генерации; float32 — точность |
| Маска m | токены, выбранные моделью (вызовы, аргументы, `<|im_end|>`); промпт, выдача, вставленные средой разделители — вне loss | Учим только решения модели. Токен j оценивается логитами позиции j−1; исходные token_ids сохраняются |
| Усреднение | по токенам: N — число маскированных токенов во всём шаге | Деление на длину каждого ответа наказывает длинный неверный ответ слабее на токен — неверные ответы раздуваются, верные укорачиваются (Dr. GRPO, DAPO). Следствие: длинные эпизоды с поиском весят больше |
| KL | к опорной модели; β = 0,02 фиксированный; k2 в loss, k3 в журнал | k2 при выборке своей политикой даёт в среднем точный градиент обратного KL (k3 — градиент прямого). Фиксированный β одинаков у GRPO и PPO; адаптивный — абляцией. Это регуляризация распределения следующего токена на посещённых контекстах, не KL траектории |
| Опорная модель | исходная T-lite = та же модель с выключенным RL-адаптером (`disable_adapter`, `no_grad`) | Лишней копии весов нет; один дополнительный прямой проход |

Название в тексте: вариант GRPO с одним обновлением на пакет, средним по группе и разбросом по пакету, усреднением
по токенам и KL-регуляризацией k2. **Принято.**

### 8. Модель, оптимизатор, память

| Параметр | Значение | Обоснование |
|---|---|---|
| Старт | исходная T-lite-it-2.1 во float16 (ревизия и хеш коммита — в манифесте) | SFT размазывает распределение следующего токена и не улучшает ответы (EXP-020/021, `decisions.md`, раздел 9); она же опорная |
| RL-адаптер | LoRA на q, k, v, o, gate, up, down_proj; r = 32, α = 32, dropout 0, bias none, без rsLoRA/DoRA; A — инициализация PEFT (сид в манифесте), B = 0; `lm_head` и эмбеддинги не обучаются | LoRA на всех линейных слоях не уступает полному дообучению в RL (LoRA Without Regret); B = 0 — старт совпадает с опорной. На первом шаге градиент A = 0 — это нормально |
| Точность | LoRA во float32, база float16 под autocast | V100 без bfloat16 |
| Оптимизатор | AdamW, lr 1e-5, betas (0,9; 0,95), eps 1e-8, wd 0, постоянный lr без разогрева | lr — стартовая настройка (LoRA — примерно в 10 раз выше полного дообучения; эмпирический ориентир, проверяется пилотом). β₂ = 0,95 быстрее реагирует на смену масштаба градиента. Weight decay не нужен: от ухода держит KL |
| Отсечение градиента | норма 1,0 | Разовый огромный градиент не портит веса и моменты Adam |
| GradScaler | после накопления: unscale → отсечение → step → update → zero_grad | Во float16 мелкие градиенты обнуляются; масштаб внутри шага не меняется; пропуск обновления — в журнал |
| Накопление | микропакет = 1 эпизод, один `optimizer.step` на шаг | Длинные эпизоды; одно обновление на пакет — условие μ = 1 |
| Память | `use_cache=False`; чекпоинтинг (`use_reentrant=False`); SDPA с выключенным наивным ядром (`enable_math_sdp(False)` — ошибка вместо тихого перехода на O(L²) памяти); логиты кусками по 1024; log-softmax, k2 и суммы во float32; `expandable_segments` | Логиты по словарю ~150 тыс. и внимание на длинном контексте — главные потребители |
| Нехватка памяти | обновление не выполняется, запуск останавливается; предел контекста уменьшается и запуск повторяется (новая конфигурация для обоих алгоритмов) | Пропуск эпизода систематически выбрасывал бы длинные эпизоды (в основном с поиском) и оставлял в градиентах часть сбойного |
| Карты | GPU 0 — обучение и опорная; GPU 1 — vLLM и bge-m3 | Веса нужны на обеих картах (градиент через vLLM не посчитать) |

### 9. Validation, судья, выбор чекпоинта

- **Каждые 10 шагов**: адаптер сохраняется (хранятся все), и он же генерирует 32 эпизода validation (8 фиксированных
  тем × 2 режима × 2 ответа; сиды — validation / задание / режим / номер ответа, без номера шага). Сразу считаются
  награда и аналитика. Ответы исходной модели на эти же задания сгенерированы один раз и сохранены.
- **Судья — отдельный асинхронный процесс**: забирает сохранённые ответы по мере появления; обучение его не ждёт,
  при сбое API он догоняет позже. Судья видит запрос и две презентации текстом под метками A и B (случайный порядок),
  не знает, какая модель что писала, и выбирает лучшую или «равны» по критериям: верность фактов, раскрытие темы,
  логика, понятность, уместность визуала, выполнение требований запроса. Две кривые:
  - (а) **доля побед над исходной** (качество): 32 пары «ответ чекпоинта — ответ исходной модели на то же задание»;
    (победы + ½ ничьих) / пары; интервал — бутстреп по темам;
  - (б) **согласие награды с судьёй** (надёжность награды, только сигнал и анализ): 16 пар — два ответа чекпоинта
    на одно задание (независимые ответы — случайная пара; отбор лучшего и худшего по награде завысил бы согласие);
    пары с |Δr| < 0,1σ не считаются, их число пишется.
  - ~48 вызовов на проверку, ~720 на запуск.
- **Кривые**: каждые 10 шагов обучающий процесс сразу дописывает в журнал запуска точку награды и аналитики
  validation; судья дописывает точки (а) и (б) того же чекпоинта, когда оценит все его пары (с запаздыванием).
  Ячейка тетрадки перечитывает журнал и рисует кривые — их видно по ходу обучения.
- **Ранней остановки нет** (решение 08.11.2026): все запуски идут ровно 150 шагов. Все чекпоинты сохраняются, и лучший
  выбирается после запуска, поэтому остановка сэкономила бы только время видеокарты, но добавила бы пороги, риск
  оборвать запуск на временной просадке и неравную длину запусков (хуже сравнение и полные кривые). Если по кривым
  видно, что запуск явно сломался, могу остановить его вручную — это не правило протокола. Если время шага
  на пилоте окажется слишком большим, число шагов уменьшается для всех запусков сразу.
- **Неоценённые пары**: ошибки API — повтор запроса; если пара так и не оценена, очередь и результаты сохраняются,
  оценка получает статус «не завершена» и может быть возобновлена; до её завершения итоговый чекпоинт не выбирается,
  а сбой судьи не считается основанием выбрать исходную.
- **Выбор чекпоинта** (после оценки всех сохранённых чекпоинтов): 3 лучших по (а) → слепой судья на полном validation
  (25 тем × 2 режима = 50 пар) против исходной → лучший. Если у лучшего (победы + ½ ничьих) / 50 ≤ 50% — итог запуска — исходная
  («RL не дал улучшения»); строго больше 50% — кандидат. Интервал показываем, решение — по точечной оценке.
  Признаки лазеек в выборе не участвуют: они не доказывают лазейку, а судья награду не видит.
- **Судья — открыто**: до RL проверяется согласие кандидатов с моей разметкой (пары EXP-013), случайный порядок —
  против предпочтения позиции. Ошибки судьи исправимы: все чекпоинты сохранены и могут быть переоценены. Нет годного
  судьи — запасной путь: выбор по награде на validation и мой просмотр финалистов.
- **Test** — одна финальная кампания оценки всех выбранных моделей, без последующего подбора: исходная (T 0,9), SFT
  (эпоха 4; T 0,9 и top-k 20), выбранные чекпоинты GRPO и PPO (`decisions.md`, раздел 9).

### 10. Аналитика (не награда и не выбор)

- **Опора на прочитанное** (режим с поиском): доля чисел и имён со слайдов, найденных в показанной модели выдаче;
  эпизоды без чисел и имён не входят в среднее (их число — отдельно). Рядом — доля слайдов со ссылкой на прочитанное.
  Ограничение: совпадение числа или имени с источником не доказывает верность утверждения.
- **Доля эпизодов с поиском** — среди заданий с разрешённым поиском; меньше лишних вызовов — ожидаемо.

### 11. Чекпоинты и воспроизводимость

- Адаптер: экспорт для vLLM — каждый шаг; архив — каждые 10 шагов, хранятся все (~15 на запуск).
- Полное состояние (оптимизатор, scaler, генераторы, счётчики сбора и обновлений, остатки очередей обоих режимов,
  потраченные токены и время) — каждые 5 шагов (`save_every`, решение 13.11.2026: три сбоя подряд до первого
  сохранения на 10-м шаге), хранятся две последние точки, на границе шага.
- **Продолжение после сбоя** (сервер упал, ядро перезапущено): тот же запуск с флагом продолжения поднимает последнее
  полное состояние (теряется до 5 шагов, они пересчитываются). Журналы (`steps.jsonl`, `validation.jsonl`,
  `judge.jsonl`) только дописываются; записи шагов после восстановленной точки помечаются как отменённые и при
  построении кривых не учитываются, дальше файлы продолжают писаться. Процесс судьи по своему журналу видит,
  какие чекпоинты уже оценены, и продолжает с первого неоценённого. Кеш Википедии сохраняется по ходу и не теряется.
  Папка запуска при продолжении **не меняется**: её имя — время первого старта, это идентификатор запуска; продолжение
  получает путь к ней. Время каждого старта (сессии) и хеш кода пишутся в манифест, время каждой записи — в журналы.
  Новая папка — только для нового запуска; если между сессиями изменились код или настройки, это не продолжение,
  а новый запуск.
- Сиды обучения выводятся из идентификаторов (запуск / шаг / задание / номер ответа / ход инструмента) стабильным хешем.
- Кеш Википедии: каждый запуск начинается с одного и того же снимка; при промахе разрешён сетевой запрос; все новые
  ответы и ревизии сохраняются.
- **Манифест** запуска: ревизии модели и токенизатора, хеш коммита исходной модели, шаблон чата, версии и хеши кода DSL, награды
  и инструментов, снимок кеша, конфигурация судьи и обоих окружений, параметры «по пилоту», правила ошибок,
  завершения эпизода и выбора чекпоинта.

### 12. Журнал (каждый шаг)

Награда (обрезанная) и компоненты по режимам, включая необрезанную, и доля обрезанных; среднее и максимум |A|, std шага, срабатывание порога 0,02, точные ничьи; KL
к опорной (k3); KL(old‖new) по log p до и после обновления на части эпизодов; полная энтропия на токенах модели;
норма градиента, пропуски обновлений, неконечные значения; длины и причины завершения (stop / length / max_turns /
контекст; доли оборванных по контексту и по пределу токенов — по режимам, на кривых), обрезанные эпизоды; ошибки разбора и отрисовки; вызовы по инструментам, реальные запросы к Википедии
(с длительностью), попадания в кеш, ошибки инструментов; доля поиска среди заданий с поиском; доли ошибочных вызовов, поисков без результатов, запросов на английском
и повторных поисков (больше половины найденных статей уже находили прежние поиски эпизода);
формат DSL по режимам — доля корректных строк, доля ответов без ошибок разбора, ошибки по кодам;
доли ответов с планом (`#PLAN`) и с заключением (среди всех и среди тем, где оно ожидается);
число слайдов и попадание в ожидаемый диапазон (запросы с числом слайдов и без — отдельно, плюс среднее отклонение);
число визуалов и картинок на эпизод, доля не связанных со слайдом среди проверенных (картинки и остальные виды отдельно); расхождение log p
vLLM; время генерации, награды, обучения, обмена адаптером и сети; пиковая память; токены — сгенерированные,
выдача, префилл, обучающие.

### 13. Проверки до длинных запусков

1. Старт: политика с нулевым RL-адаптером = опорная в пределах погрешности, KL ≈ 0, градиент k2 = 0.
2. log p vLLM ≈ `transformers`; переключение адаптеров A → B → A возвращает прежние вероятности.
3. Накопление по эпизодам = целый пакет при общем N (маленькая модель).
4. Маски на эпизоде с двумя репликами и выдачей: сдвиг, `<|im_end|>`, исключение вставленного средой.
5. Средний градиент k2 = градиент точного KL на маленьком категориальном распределении.
6. На контролируемой маленькой задаче обновление повышает вероятность полезного действия.
7. Память (одна проверка): GPU 0 — полный шаг на эпизоде с максимальным контекстом и 8000 токенов модели (политика,
   опорная, создание состояния Adam), наивное ядро выключено; GPU 1 — пиковая нагрузка vLLM вместе с bge-m3.
8. Награда на фиксированных контрпримерах (неверное число, выдуманная цитата, повтор вызова, вызов без поиска).
9. Продолжение с чекпоинта: тот же update на сохранённом пакете.
10. Пилот (`notebooks/grpo_pilot.ipynb`, папка `runs/grpo_pilot/`): 3 шага с validation на третьем — время сбора,
    награды, обучения, публикации адаптера и validation, оценка полного запуска; весь путь на настоящих данных
    (журналы, адаптер шага в vLLM, чекпоинт, состояние). По нему решается, остаются ли 150 шагов.

### 14. Сравнение с PPO

Согласовано с научным руководителем: GRPO и PPO сравниваются в своих конфигурациях при одинаковых условиях
эксперимента — задания, награда, среда, модель, старт (исходная T-lite), железо и одинаковый бюджет: ровно 150 шагов сбора
= 9536 обучающих эпизодов (148 × 64 + 2 неполных шага × 32). Параметры обучения различаются (GRPO μ = 1; PPO μ = 2–4, выбирается при
проектировании PPO) и сводятся в сравнительную таблицу. Фактические токены и время каждого запуска (включая неудачные
попытки и пропущенные обновления; сетевое время отдельно) показываются рядом. Вывод относится к конфигурациям целиком:
без абляций влияние только алгоритма не выделяется. По 2 сида на алгоритм, результаты обоих запусков — отдельно
(бутстреп по темам — неопределённость по темам, не вариативность обучения).

## Часть 2. Как это описать в статье

### Обучение с подкреплением: GRPO

Политика обучается методом Group Relative Policy Optimization (GRPO) [Shao et al., 2024] в варианте с одним
обновлением на собранный пакет. Начальная политика — исходная T-lite-it-2.1: дообучение на примерах сильных моделей
расширяло распределение следующего токена и ухудшало ответы (раздел X). Эта же модель служит опорной для KL-регуляризации. Поверх
неё обучается новый адаптер LoRA ранга 32 (α = 32) на всех линейных слоях блоков трансформера; на старте его
поправка нулевая, и политика совпадает с опорной.

**Сбор данных.** Обучающая выборка — 274 темы, каждая в двух режимах: с доступом к поиску по Википедии и без него;
одна модель обучается обоим режимам одновременно. На каждом шаге берутся 8 заданий, по 4 каждого режима, и на каждое
генерируются G = 8 эпизодов. Эпизод — диалог агента со средой: модель может вызывать инструменты `search`, `open`
и `read` (не более 10 вызовов) и завершает эпизод презентацией в построчном DSL. Генерация выполняется в vLLM
[Kwon et al., 2023] при температуре 0,9 без отсечения хвоста распределения (top-k и top-p выключены явно), поэтому
вероятности при обучении считаются по тому же распределению, из которого выбирались токены. Эпизод ограничен
12 000 токенами модели и общим пределом контекста.

**Награда и преимущество.** Каждая презентация получает скалярную награду r (раздел X): покрытие тезисов темы,
ключевые факты, длина, визуальные элементы, формат и штрафы за ошибки и лишние вызовы инструментов; снизу награда ограничена значением −1, чтобы сложенные
штрафы отдельных провальных ответов не раздували разброс наград пакета. Преимущество
ответа — отклонение его награды от среднего по группе, нормированное на разброс наград во всём пакете:

A_i = (r_i − mean_{j∈g(i)} r_j) / max(std_{j∈B} r_j, 0,02).

Среднее по группе заменяет обучаемый критик PPO и убирает различия в сложности заданий: ответ, оказавшийся хуже
соседей по группе, получает отрицательное преимущество, даже если его награда положительна. Нормировка на разброс
пакета, а не группы [Liu et al., 2025b], не даёт группам с почти равными ответами получать сигнал того же размера,
что группам с явным победителем [Liu et al., 2025a]; нижняя граница знаменателя (около четверти типичного разброса
награды внутри задания) защищает от раздувания сигнала, когда ответы почти неразличимы.

**Функция потерь.** Обучение ведётся только на токенах, выбранных моделью; промпт и выдача инструментов исключаются
маской. Потери усредняются по всем таким токенам пакета, а не сначала внутри ответа: деление на длину ответа
наказывает длинные ошибочные ответы слабее в пересчёте на токен [Liu et al., 2025a; Yu et al., 2025].

L(θ) = (1/N) Σ_{i,t} [ −A_i · ρ_{i,t}(θ) + (β/2) (log π_θ(y_{i,t}|h_{i,t}) − log π_ref(y_{i,t}|h_{i,t}))² ],

где N — число токенов модели в пакете, ρ_{i,t} = π_θ / π_old, β = 0,02. Поскольку на каждый пакет делается одно
обновление, π_old совпадает с π_θ, ρ = 1 и клиппинг PPO не активируется; градиент первого слагаемого равен градиенту
политики −A ∇log π_θ. Квадратичная оценка KL (k2) [Schulman, 2020] при выборке из текущей политики даёт в среднем
градиент обратного KL к опорной модели на посещённых контекстах; значение KL для мониторинга оценивается
несмещённой оценкой k3. Коэффициент β фиксирован и одинаков для GRPO и PPO.

**Оптимизация.** AdamW (lr = 10⁻⁵, β₁ = 0,9, β₂ = 0,95, без weight decay), постоянная скорость обучения, отсечение
нормы градиента на 1,0. Из-за отсутствия bfloat16 на V100 базовые веса хранятся во float16, адаптер — во float32,
используется динамическое масштабирование потерь. Градиенты 64 эпизодов накапливаются по одному эпизоду, обновление —
одно на шаг. Генерация выполняется на одном GPU, обучение — на другом; после каждого шага адаптер передаётся
генератору, расхождение log-вероятностей генератора и обучающего кода контролируется.

**Оценка в ходе обучения и выбор модели.** Каждый запуск длится 150 шагов (около двух проходов по заданиям), без ранней
остановки.
Каждые 10 шагов адаптер сохраняется и генерирует ответы на фиксированную часть validation. Независимый от награды
LLM-судья вслепую сравнивает их с ответами исходной модели на те же задания (доля побед) и, отдельно, проверяет, согласуется
ли награда с его предпочтениями внутри пар ответов одного чекпоинта; обе кривые строятся по ходу обучения. Итоговый чекпоинт выбирается среди трёх лучших по доле побед слепым судьёй на полном validation; если
ни один не превосходит исходную модель, результатом запуска считается исходная модель. Test используется один раз.

**Сравнение с PPO.** GRPO и PPO сравниваются в собственных конфигурациях при одинаковых условиях эксперимента
и одинаковом бюджете в 150 шагов (9536 обучающих эпизодов); различающиеся параметры приведены в сравнительной таблице. Каждый
алгоритм запускается с двумя сидами, результаты обоих запусков приводятся отдельно.
