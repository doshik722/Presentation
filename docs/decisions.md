# Принятые решения

Состояние на 29 сентября 2026 года. Если решение меняется, правим этот файл
и кратко записываем причину в раздел «История изменений».

## 1. Рамка работы

Работа одна — диплом. Он состоит из двух частей:

1. **RL-часть** (защищается как курсовая): агенты PPO и GRPO, обученные создавать презентации.
2. **LangChain-часть** (позже): агент на LangChain с теми же инструментами, сравнение с RL-агентами.

Исследовательские вопросы:

- как PPO и GRPO различаются по глубине итоговых презентаций и по эффективности обучения;
- насколько рационально давать агенту доступ к внешним источникам: один и тот же агент с поиском и без поиска
  (агент решает, что и когда искать, поиск выполняет среда);
- (диплом) чем RL-агенты отличаются от LangChain-агента при одинаковых инструментах и источниках.

## 2. Формат вывода модели — построчный DSL

Модель пишет весь текст сама, включая теги. Одна строка — один элемент: `#ТЕГ: значение`.

| Тег | Значение | Что делает сборщик |
|---|---|---|
| `#PLAN` | черновой план | пропускает |
| `#SLIDE` | без значения, начинает новый слайд | — |
| `#TITLE` | заголовок слайда | поле заголовка |
| `#TEXT` | абзац связного текста | абзац без маркера |
| `#BULLET` | пункт списка (только для настоящих перечислений) | пункт списка |
| `#FORMULA` | LaTeX (подмножество matplotlib mathtext) | PNG |
| `#CHART` | `type=bar\|line\|pie; title=...; x=...; y=...` | нативный редактируемый график pptx |
| `#PLOT` | функция и диапазон, например `y = x^2; x=-2..5` | PNG через matplotlib |
| `#DIAGRAM` | структура схемы текстом | PNG |
| `#TIMELINE` | `год — событие; год — событие` | фигуры на слайде |
| `#QUOTE` | цитата с атрибуцией | блок цитаты |
| `#IMAGE` | описание нужной картинки; только если в запросе «Картинки: есть» | картинка из Wikimedia Commons с подписью и лицензией |
| `#SOURCE` | id раздела из выдачи этого эпизода | ссылка на источник |
| `#NOTES` | заметки докладчика | заметки слайда |

Принципы:

- каждая строка разбирается независимо; битая строка теряется сама, остальные собираются;
- строки без тега и неизвестные теги считаются ошибками разбора, но не ломают презентацию;
- `parse_rate` — диагностика и небольшой компонент награды, не главный сигнал;
- модель не видит ни картинок, ни URL; она решает, что показать, а исполняет сборщик.

Точная грамматика (экранирование, числа, пустые значения, восстановление после структурных ошибок)
описывается отдельно в `docs/dsl_spec.md` до написания парсера.

## 3. Сборщик презентации

- Один сборщик для всех моделей и агентов; он не исправляет содержание и не переставляет слайды.
- Размеры шрифтов фиксированы: заголовок 30 pt, текст и цитата 20 pt, подписи 12 pt, источники 10 pt;
  подбирается только размер подписи внутри узла схемы (14–10 pt). Шрифт не уменьшается:
  не поместившийся текст отмечается в отчёте как `text_overflow` и учитывается наградой. Оценка высоты текста
  откалибрована по PowerPoint (решение 27.10.2026, `scripts/text_fit`): средняя ширина символа — 0,49 размера шрифта
  у основного текста, 0,58 у заголовков, 0,52 у цитат; строка — 1,2 размера, отступ 0,5 размера только между абзацами;
  высота формулы — по её картинке (рисуется до раскладки), а не 0,75 дюйма вслепую.
  Если под колонкой только край слайда (нет визуала и строки источников), тексту можно зайти в нижний запас
  на 0,3 дюйма (около строки); если под текстом визуал или формула — любое наложение считается переполнением.
- Макеты: «текст», «текст + 1 визуальный элемент», «текст + 2 визуальных элемента».
- Картинки: сборщик по описанию из `#IMAGE` ищет кандидатов в Wikimedia Commons и выбирает через мультиязычный CLIP;
  модель картинок не видит и не выбирает (решение 01.10.2026). Для скачивания сборщику нужен интернет; если его нет,
  ставится заглушка и запись в отчёте — это сбой окружения, а не ошибка модели. При обучении картинки не скачиваются.
- Отчёт сборщика фиксирует, какие элементы не удалось отрисовать и почему.
- Сборщик можно вызвать без файла (`build_presentation(deck, None, …)`, решение 08.11.2026): презентация собирается
  в память, отчёт тот же (число слайдов, переполнения, ошибки отрисовки). Так считается награда в проверке
  на искажениях и при обучении — без записи тысяч файлов на диск.
- Палитры (`rendering/themes.py`): 6 палитр с проверенной контрастностью текста (WCAG: основной текст ≥ 7,
  подписи ≥ 4,5). Различаются только цвета; шрифты, размеры и раскладка общие, поэтому палитра не влияет
  на заполнение и переполнение. Модель палитру не выбирает и не видит; пользователь задаёт её полем
  `theme` в запросе, по умолчанию (`auto`) палитра выбирается по тексту запроса — один запрос всегда получает
  одну палитру, разные запросы — разные.

## 4. Эпизод и агент

Для пользователя презентация создаётся за одну генерацию; внутри неё модель может обращаться к поиску.

**Один агент; поиск и картинки — два независимых поля запроса** (решение 15.10.2026, вместо отдельных этапов A и B).
Модель видит строки «Поиск: есть / нет» и «Картинки: есть / нет» и должна уметь работать при любом их сочетании.

- «Поиск: есть» — модель может вызывать поиск по Википедии и сама решает, обращаться ли к нему, что искать
  и что взять из найденного; сам поиск выполняет среда — всегда через живой API Википедии с сохранением ответов
  (раздел 5); интерфейс инструментов один и тот же при обучении, оценке и использовании.
  «Поиск: нет» — инструментов нет.
- Промпт по режимам (решение 20.10.2026): с поиском — начало «сначала найди факты в Википедии, потом пиши
  презентацию», поиск в промпте подчёркивается; без поиска — «сразу пиши презентацию», поиск и инструменты
  не упоминаются (описаний инструментов шаблон чата в этом режиме и так не получает). Вызов в режиме без поиска:
  при обучении не запрещается, а штрафуется наградой (0,1 за вызов; среда отвечает «Поиск в этом режиме недоступен.
  Пишите презентацию без него», модель продолжает, после двух отказов эпизод заканчивается; решение 27.10.2026);
  при использовании запрещён — генерации запрещено выбирать
  токен `<tool_call>` (подробно — `docs/subtleties.md`). Формулировки — `prompts.py`: без поиска — вариант B
  из EXP-008, с поиском — вариант F из EXP-009 (вызов инструмента описан в разделе «Формат», пример — эпизод
  с вызовами) и правила «не повторяй запрос с мелкими изменениями, не читай раздел дважды».
- «Картинки: есть» — модель может писать `#IMAGE`, картинку ищет сборщик. «Картинки: нет» — `#IMAGE` не используется
  и в промпте не упоминается вовсе: ни тега в формате, ни правил о картинках, ни `#IMAGE` в примере (как поиск без поиска),
  вместо картинок — графики, диаграммы, схемы; `#IMAGE` при «Картинки: нет» не рисуется, не считается визуалом
  и штрафуется.
- Источники на слайдах — по желанию пользователя (поле `sources`, по умолчанию показывать). Модели это поле
  не передаётся: при поиске она всегда пишет `#SOURCE`, а убирает их со слайдов сборщик (`show_sources=False`);
  id при этом всё равно проверяются и сохраняются в отчёте — по ним видно, откуда взят материал.
- Язык презентации — русский, если в запросе не сказано иное. Английские термины там, где они приняты в теме,
  допустимы; проверяется язык основного текста, а не отдельные слова.
- Заранее, без запроса модели, среда ничего не ищет и в промпт не подставляет.
- Все сочетания — у одной обученной модели; сравнение «с поиском / без поиска» отвечает на вопрос о доступе
  к источникам (раздел 1).

- Во время генерации модель может вызвать инструмент: генерация останавливается, система выполняет вызов,
  дописывает результат в контекст, модель продолжает с того же места. Формат — шаблон чата T-lite-it-2.1 (как у Qwen3,
  сохранён в `configs/models/tlite_21_chat_template.txt`): модель пишет `<tool_call>{"name": …, "arguments": {…}}</tool_call>`
  и заканчивает реплику; среда выполняет все вызовы реплики и дописывает реплику user с блоками `<tool_response>`,
  затем новую реплику assistant с пустым блоком рассуждений (`<think>\n\n</think>`, как `add_generation_prompt`
  шаблона: режим рассуждений не используем). Реализация — `environment.py` (`run_episode`).
- Эпизод собирается по ходу генерации и не пересобирается шаблоном чата: шаблон ставит пустой `<think>` только
  у последней реплики, и пересборка дала бы текст, которого модель не видела (подробно — `docs/subtleties.md`).
  Примеры SFT с поиском составляются той же функцией эпизода.
- Эпизод хранится токенами, а не текстом (логарифмы вероятностей в RL — по тем же токенам, что сгенерированы);
  куски помечены «модель» / «инструмент и разметка», отсюда маска loss. Генерация передаётся функцией, среда от неё
  не зависит. Неразобранный вызов (не JSON, неизвестный инструмент, незакрытый тег) получает ответ с ошибкой и тратит
  вызов из лимита. Без поиска вызовы не выполняются: текст идёт парсеру и становится ошибкой разбора.
- Инструменты модели: `search`, `open`, `read` — в штатном формате вызова инструментов модели (решение 16.10.2026).
  Поиск, как и у Википедии, — по статьям; дальше модель сама открывает статью и выбирает раздел.
  Текст из разных мест не склеивается:
  - `search(запрос)` — до 3 статей из поиска Википедии на языке запроса (язык — по алфавиту, см. раздел 5)
    и до 3 их версий на другом языке; страницы значений пропускаются. По каждой — id статьи (`d3`), язык,
    название и первые ~200 символов введения. В описании инструмента: запрос — 1–4 ключевых слова, а не фраза
    (поиск Википедии длинные фразы понимает плохо);
  - `open(id статьи)` — введение и полное оглавление статьи (все уровни, id разделов вида `d3#5`) с подводками
    разделов, у которых есть подразделы (подводка — текст между заголовком и первым подразделом). Лимит 6000 символов:
    заголовки показываются всегда; если введение и подводки не помещаются, обрезаются только самые длинные —
    до наибольшего порога, при котором всё помещается (на пилоте введение и оглавление без подводок помещаются
    в 99% статей; что-то из подводок обрезается в 16% русских и 28% английских статей с подразделами);
  - `read(id раздела)` — текст одного раздела без подразделов (у раздела с подразделами — его подводка); лимит
    6000 символов (целиком помещаются 94% русских и 95% английских разделов), длинный обрезается по границе абзаца
    с пометкой «обрезано, ещё N символов».
  - Текст разделов — простой текст API Википедии; таблиц в нём нет, поэтому таблицы (`wikitable`) и карточка статьи
    (infobox) берутся из HTML той же правки и дописываются в конец своего раздела: «Таблица: подпись», строки ячеек
    через « | »; карточка — «Карточка статьи:», «поле: значение», в конце введения (`tools/wiki_tables.py`,
    решение 20.10.2026).
- Id живут только внутри эпизода (эпизод — один прогон модели на одном задании): статьи нумеруются `d1`, `d2`…
  по порядку появления, номер раздела — его порядковый номер в статье. Среда хранит таблицу «id → язык, номер
  страницы Википедии», в конце эпизода она пишется в лог вместе с ответом.
- Оглавление основной статьи в промпт **не даём**: модель получает его только по своему вызову `open`.
  Риск, что модель станет перекладывать оглавление Википедии в слайды, отслеживаем метрикой анализа
  (совпадение порядка слайдов с оглавлением); тезисы test из оглавления не копируются.
- Картинки — не инструмент модели: модель пишет описание в `#IMAGE`, ищет и выбирает картинку сборщик
  (Wikimedia Commons + CLIP). Если смотреть на систему целиком, это исполнительный инструмент:
  модель объявляет, что нужно, система выполняет после генерации; модель результата не видит.
- Вызов возможен в любом месте генерации. Парсер получает всё, что написала модель, по порядку,
  без блоков вызовов и результатов; план перед вызовом пишется тегом `#PLAN`.
- `#SOURCE` содержит id из этого эпизода: `d3` — статья из выдачи `search`, `d3#5` — раздел (`d3#0` — введение)
  открытой статьи; ссылку и оформление источников делает сборщик.
- Лимиты: 8–10 вызовов (точное число — по пилоту, с учётом длины контекста на V100), ограничение объёма
  прочитанного текста, небольшая стоимость каждого вызова. При трёх шагах «поиск → оглавление → раздел» 5 вызовов
  хватает только на один-два раздела.
- Повтор вызова слово в слово (тот же инструмент и тот же аргумент, без учёта пробелов по краям) среда не выполняет:
  модель получает ответ «Такой запрос уже был, результат выше» (решение 27.10.2026). Вызов при этом тратится из лимита;
  штраф за повтор — в награде (раздел 7).
- Для RL это многошаговый эпизод: результаты инструментов написаны не моделью и исключаются из loss маской.
- Перед вызовом модель может коротко написать план или причину выбора (`#PLAN`), но не обязана: T-lite не обучена
  режиму рассуждений, заставлять её не будем. Отдельной абляции «с мыслью / без мысли» нет.
  Длина текста между вызовами ограничена техническим лимитом токенов, без штрафа в награде.
- Среда и цикл генерации пишутся с поддержкой вызовов инструментов; ответ без вызовов — частный случай.

Многошаговое редактирование уже готовых слайдов отложено.

## 5. Источники

- Поиск — **живой API Википедии с сохранением ответов** (решение 16.10.2026, вместо заранее собранного корпуса):
  модель и при обучении, и при оценке, и при использовании получает настоящую выдачу Википедии. Каждый ответ API
  (выдача поиска, статья по разделам, межъязыковые ссылки) сохраняется и повторно не запрашивается: роллауты GRPO
  повторяют задания и запросы, так что большая часть вызовов берётся из сохранённого. Сохранённое фиксирует
  состояние Википедии: повторные прогоны и сравнения (test, LangChain-агент) идут по тем же ответам, новые запросы
  дописываются. Статьи хранятся по разделам с id ревизии и датой; метаданные картинок берутся из тех же статей.
- Язык поиска — по алфавиту запроса: есть кириллица — русская Википедия, иначе английская. Модель сама решает,
  на каком языке искать (для технических тем английская Википедия часто полнее); в примерах SFT с поиском
  составители иногда пишут запросы на английском.
- Выдача `search`: до 3 статей из поиска на языке запроса и их версии на другом языке по межъязыковым ссылкам,
  язык помечен (раздел 4). Своего ранжирования у нас нет: порядок статей — как у Википедии, раздел выбирает модель.
- Запросы к API — по одному, с паузой 0,5 с, контактом в User-Agent и повтором при перегрузке; при параллельных
  роллаутах — общая очередь. Промах стоит 1–2 с — мало по сравнению с генерацией (порядка минуты на ответ на V100).
  Сервер выходит в интернет (проверено 16.10.2026).
- Хранилище сохранённых ответов: приватный датасет Kaggle с версиями; на сервере — локальные файлы.
  Ответы пилота (`data/sources/wiki_pilot/`) переносятся в него.
- LangChain-агент получает те же инструменты, те же сохранённые ответы и те же лимиты.
- Сохранённые ответы не кладём в git. Тексты Википедии — CC BY-SA: при публикации указываем авторство и ту же лицензию.

## 6. Задания и данные

Запрос пользователя — `PresentationRequest` (`src/presentation_rl/tasks.py`): текст запроса и необязательные поля
`audience` (нет — модель выбирает сама), `slides` (число или диапазон), `domain` (`technical` / `humanities` / `auto`,
по умолчанию `auto`), `search` и `images` (по умолчанию включены; пользователь может выключить). Модель получает
текст запроса и заполненные поля.

- Число слайдов: если оно задано полем или в тексте («на 7 слайдов», «5–7 слайдов», «для слайда», «15 страниц»),
  требование берётся оттуда; если поле и текст противоречат друг другу, решает поле. Больше 30 не бывает (лимит
  парсера; просьба больше 30 урезается до 30). Не задано нигде — требования нет, модель выбирает число слайдов сама.
- Задание набора (`Task`, `data/tasks/tasks.json`) — запрос плюс сведения для выборок и отчёта: `split`, `source`,
  `family`, `scenario`, `discipline`, `has_course`, `has_material`. Темы из рабочих программ подаются как
  «Сделай презентацию на тему «…»» с аудиторией и типом темы; запросы WildChat и составленные — текстом пользователя,
  тип темы `auto`. `load_tasks` проверяет набор: уникальные id, одно семейство — одна выборка, непустой текст,
  допустимое число слайдов.
- Тезисы (`key_points`) хранятся отдельно от заданий.

- `domain` определяется по природе темы: `technical` — понятия, законы, модели, методы (инфляция — сюда);
  `humanities` — события, процессы и идеи в истории. Модели передаётся как подсказка, не как требование
  (награда на тип не смотрит): в технической теме обычно важнее механизмы, формулы и графики, в гуманитарной —
  события, причины и следствия, ленты времени и цитаты; это объяснение есть в промпте составителей и будет
  в системном промпте модели. По `domain` делим выборки
  и показываем метрики по типам.
- `key_points` и `expected_elements` модель **не видит**; их использует только оценка.
- Источники заданий (под наличие хороших статей Википедии темы не подбираются; если в Википедии мало материала,
  это часть задачи агента):
  - учебные темы из рабочих программ дисциплин российских вузов: 36 дисциплин поровну по типам, 72 программы,
    837 сырых тем (`data/tasks/raw_topics.json`, ссылки на документы — `raw_topics.md`);
  - реальные запросы пользователей из WildChat-1M (ODC-BY): русские диалоги с просьбой о презентации,
    отбор — `data/tasks/wildchat_requests.xlsx`, столбец «Беру»;
  - составленные запросы для сценариев, редких в WildChat (быт, научпоп, рабочие отчёты с данными):
    в таблице с id `автор` или `составлено`; в работе указывается их число отдельно от реальных.
  Отобрано из запросов 294: учёба 213, работа 35, быт 33, научпоп 9, другое 4. Берутся все; из рабочих программ —
  155 тем, в среднем по 4 на дисциплину, равномерно по курсу (`data/tasks/syllabus_topics.xlsx`: 674 очищенные темы-семейства,
  столбец «Порядок»). Итого 449 заданий; внеучебных около 20%, как в реальных запросах (в WildChat учёба — около 70%).
- Рабочие запросы содержат исходные данные (цифры, итоги), как у реального пользователя: иначе модели пришлось бы
  их выдумывать. Творческие и развлекательные задания (мемная презентация, хронология вечера) допускают 0 контрольных
  фактов; в промпте тезисов это нужно разрешить.
- `key_points` обучения **не совпадают с оглавлением одной статьи**, иначе RL поощрял бы копирование её структуры.
  Черновики составляют три LLM разных разработчиков (Claude, GPT, Gemini): темы делятся между ними поровну,
  у каждой темы один черновик. Деление случайное, стратифицированное по `domain` и выборке (train/validation/test),
  чтобы особенности модели не совпали с типом темы. Промпт и формат ответа у всех одинаковые
  (`data/tasks/key_points_prompt.txt`); на входе — id, тема и аудитория. Разделы статей Википедии
  не даём, чтобы тезисы не повторяли их структуру: модель опирается на веб-поиск и свои знания о курсах по теме.
  Обучаемые и сравниваемые модели (T-lite, Qwen) черновики не составляют.
- Условия составления одинаковые у всех трёх моделей: каждая пачка тем — в новом чате, без памяти и истории
  разговоров (весь контекст — в опубликованном промпте); веб-поиск включён, модель перечисляет источники,
  на которые опиралась. Сырые ответы со списками источников сохраняются без правок, вместе с названием модели и датой.
- Точно повторить черновики нельзя (случайная выборка в чате, меняющаяся выдача поиска, обновления моделей в чатах),
  поэтому воспроизводимость обеспечивают опубликованные итоговые списки, промпты и сырые ответы, а не повторная генерация.
- Ответ модели на тему (JSON): тезисы по числу слайдов задания (один тезис на 1–2 содержательных слайда, без титульного;
  если слайдов больше трёх, последний тезис — заключение (выводы); не больше 13, не считая заключения; если число слайдов не задано — сколько нужно для раскрытия темы, не больше 13) —
  `title` (название части темы, как заголовок слайда, до 8 слов), `statement` (одно предложение до 25 слов:
  что слайд должен донести — утверждение, а не тема) и `key` (5–7 слов и сочетаний по 1–4 слова, которые
  обязательно будут в тексте слайда: годы, числа, имена, названия, термины; в той форме, как на слайде; без формул
  и общих слов); данные из запроса пользователя обязательно входят в `key`; при презентации на другом языке
  тезисы на этом языке. Отдельных контрольных фактов (`claim`) нет — их роль у `statement` и `key` (решение
  23.10.2026). Источники — только в validation и test, для ручной проверки. У заданий не из рабочих программ
  составитель получает и полный текст запроса. Аудитория знает базовые понятия своей области: тезисы раскрывают тему
  глубоко, азы отдельными тезисами не выносятся. Роль («ты — преподаватель») в промпте не задаём.
  Не просим: веса, подсказки для поиска, структуру
  презентации, «что за рамками аудитории», пометки неуверенности, типичные ошибки.
- Для каждой темы хранится, какая модель составила черновик. Все черновики проверяются и правятся вручную,
  при необходимости — по учебникам и программам курсов. Итоговые списки фиксируются до обучения.
- LLM-судья на validation/test — модель, которая черновики не составляла, или это оговаривается в работе.
- `key_points` без весов: GRPO сравнивает ответы на одно задание между собой, поэтому общий «потолок»
  покрытия (например, мало слайдов на большую тему) на сравнение не влияет.
- SFT: около 90 полных примеров презентаций в DSL — по 30 от Claude, Codex и Gemini (те же модели, что составляют
  тезисы: перенять их представление о раскрытии темы — желательно). Черновики проверяются и исправляются вручную.
  Примеры: без картинок — 35 из 90, с картинками — 55; все без вызовов поиска и в наборе идут с «Поиск: нет»
  (иначе модель выучит, что при доступном поиске искать не нужно).
  Отдельно — примеры с «Поиск: есть», вызовами `search`/`open`/`read` и `#SOURCE`: их составляем после
  инструментов (пункты 6–7 плана), на реальных результатах поиска, так что каждый id в `#SOURCE` проверяется кодом.
  Порядок: составитель получает запрос и описание инструментов и пишет план и вызовы; вызовы выполняет скрипт
  через те же инструменты, результаты возвращаются составителю, и он пишет презентацию с `#SOURCE` (при необходимости —
  ещё вызовы). Картинки в этих примерах тоже бывают и есть, и нет.
  Если после SFT модель на отложенных темах плохо держит формат, примеры добавляются.
- validation (~25) и test (~60) составляются и проверяются вручную; `key_points` для test не копируются из оглавления статьи.
  Протокол: черновик тем же способом, что и для обучения (те же три модели), плюс обязательная сверка с 2–3 источниками
  (программы курсов и ФГОС, оглавления учебников) → правка → фиксация до обучения; протокол и источники описываются в работе. Источники нужны только для составления
  списка тезисов человеком: модели они не выдаются, хранится только список тезисов.
- Четыре непересекающиеся выборки: SFT (90), train для RL (274), validation (25), test (60); набор — `data/tasks/tasks.json`,
  описание и статистика — `docs/dataset.md`.
  Темы SFT в RL не используются: модель запоминает содержание примеров, и на этих темах роллауты повторяли бы
  запомненный ответ — группа без разброса и завышенная награда. Тезисы составляются только для train, validation и test.
- Разделение по семействам тем: перефразировки одного задания не попадают в разные выборки;
  в test есть семейства тем, которых нет в обучении. Test не используется для настройки.
- Типы тем сбалансированы, деление стратифицировано по `domain`; метрики в отчёте — по типам отдельно.
- Любую тему можно раскрыть по-разному (градиентный спуск — в методах оптимизации и в машинном обучении).
  Эталон тезисов фиксирует одно разумное прочтение — то, которое чаще ожидают от указанной аудитории;
  списков тезисов для разных прочтений не делаем. Смещение случайное (разные темы и составители), а не
  систематическое; покрытие тезисов — лишь часть награды, на validation/test качество оценивает судья.
  В работе это записывается как ограничение.
- Аудитория в заданиях бывает двух видов: с курсом или дисциплиной («студенты старших курсов на занятии по дисциплине
  „Педагогика“») и без них. Курс добавлен к 20% тем из рабочих программ (31, не больше одной на дисциплину); у запросов
  из WildChat — только если его назвал пользователь (15). Всего с курсом 46 заданий (10%); в test — 12 из 60 (20%),
  чтобы метрики по заданиям с курсом можно было показать отдельно. Темы из программ подаются как «тема + аудитория»,
  запросы из WildChat — текстом пользователя (аудитория указана в 37 из 262).
  Пользователю демо рекомендуем указывать курс или дисциплину: тогда прочтение темы совпадает с ожидаемым.

## 7. Награда при обучении

| Компонент | Правило |
|---|---|
| Полнота | покрытие `key_points`: для каждого тезиса — сходство с ближайшим по смыслу слайдом (0,15 × `title`↔заголовок + 0,85 × `statement`↔содержание), затем среднее по тезисам темы; без порога. Тезис-заключение — только с последним слайдом |
| Ключи | доля `key` тезиса, найденных дословно на двух его лучших слайдах (каждый ключ считается один раз), среднее по тезисам; штрафа за содержание сверх ключей нет |
| Ошибки | элемент не отрисован (`render_error`: формула не собирается, выражение графика не считается) — −0,5 в визуальной сумме; `#SOURCE` с id не из этого эпизода (`bad_source`) — −0,1 за каждый |
| Визуал | бонус за каждый засчитанный визуальный элемент до предела ⌈0,5·N⌉ на тип (картинки — N) и 2·N всего; формулы отдельно — 0,7 за каждую до 2·N, сверх — −0,2; штраф за каждый сверх предела (N — содержательные слайды) и за каждый не нарисованный сверх ограничения слайда (2 крупных, 3 формулы); неудачный график и непроверенная цитата не засчитываются |
| Формат | штраф `1 − parse_rate` (доля битых строк) с малым весом; 0,1 за каждый слайд, где текст не поместился в колонку (`text_overflow`) |
| Длина | штраф за число слайдов вне ожидаемого диапазона: заданного в запросе или выведенного из числа тезисов (множитель 1,3) |
| Инструменты | при «Поиск: есть» — стоимость каждого вызова и штраф 0,1 за каждый повтор; при «Поиск: нет» — штраф 0,1 за каждый вызов |
| Запреты запроса | штраф за `#IMAGE` при «Картинки: нет» (такой элемент ещё и не считается визуалом) |

- При обучении картинки не скачиваются: оценивается только запрос или описание картинки.
- Покрытие (решение 23.10.2026). Тезис `i` = `title` + `statement` + `key`; слайд `s` = заголовок `T` + видимое
  содержание `C`. Сходство `sim(i, s) = 0,15 · cos(title_i, T_s) + 0,85 · cos(statement_i, C_s)`: каждая часть тезиса
  сравнивается со своей частью слайда. Только заголовок можно обмануть правильным заголовком над пустым слайдом,
  поэтому вес заголовка мал; утверждение, а не список понятий, отличает объяснение от перечня слов. Веса проверяются
  на испорченных презентациях. Покрытие тезиса — `sim` с лучшим слайдом; итог — среднее по тезисам, поэтому число
  тезисов в теме на шкалу не влияет. Если слайдов больше трёх, последний тезис — заключение: он сравнивается той же
  формулой только с последним слайдом (без автоматического слайда «Источники») и в выбор лучшего слайда не входит;
  требование заключения задаётся эталоном, а не длиной ответа. Последний слайд при этом не участвует в выборе лучшего
  слайда для остальных тезисов (решение 27.10.2026): заключение сравнивается только с заключением. Иначе итоговый
  слайд, перечисляющий всё понемногу, оказался бы лучшим сразу для нескольких тезисов, и модели стало бы выгодно
  переносить содержание в заключение. Качество заключения, вероятно, нужно оценивать и отдельной метрикой (раздел 8).
- Лексическая часть сходства (кандидат, решение 26.10.2026). К смысловому сходству утверждения добавляется доля
  слов `statement`, найденных на слайде (делится на число слов утверждения; длина слайда в формулу не входит,
  подробный слайд не наказывается): слова приводятся к начальной форме тем же лемматизатором, что и ключи,
  служебные отбрасываются. `sim(i, s) = 0,15 · cos(title_i, T_s) + 0,85 · [(1 − α) · cos(statement_i, C_s) +
  α · доля_слов(statement_i, C_s)]`, α ≈ 0,2–0,3. Эмбеддер размыт и почти одинаково оценивает слайд «о том же
  в общем» и слайд, говорящий именно то, что в утверждении; совпадение слов это различает и уточняет выбор лучшего
  слайда, от которого зависят и ключи. Подгонки нет: утверждения модель не видит. Вместо BM25 — доля слов: шкала
  сразу [0, 1], не нужны нормировка и корпус для IDF, а в утверждении 10–25 слов, так что насыщение и IDF почти
  ничего не дают. Вводится и α подбирается на испорченных презентациях: правильный слайд должен лучше отделяться
  от чужого и от пустого с правильным заголовком, а перефразировка не должна заметно снижать награду (поэтому α мало).
- Визуал (решение 26.10.2026, формулы — 28.10.2026). Визуальные элементы: `#CHART`, `#PLOT`, `#DIAGRAM`, `#TIMELINE`,
  `#IMAGE`, `#QUOTE`. Формула — не визуальный элемент: в пределы визуала не входит, засчитывается отдельно — +0,7 за
  каждую до 2·N на презентацию, сверх — −0,2 и без бонуса (в той же сумме); без бонуса модель видела бы в формулах только штрафы
  и избегала бы их в технических темах. N — число содержательных слайдов (без титульного и заключения). Каждый тип засчитывается до ⌈0,5·N⌉
  элементов (картинки — до N, решение 29.10.2026), все типы вместе — до 2·N; каждый засчитанный элемент в пределах обоих пределов даёт +1, каждый сверх
  предела своего типа или общего — −1; сумма делится на 2·N, вес у всех типов одинаковый. Засчитываются только
  элементы, которые сборщик нарисовал без ошибок. Ограничения сборщика на слайд — 2 крупных элемента и 3 формулы —
  остаются; лишнее не рисуется, и каждый такой элемент даёт −1 в той же сумме (решение 27.10.2026): одно правило
  «сверх предела — минус один» для общего предела и для слайда, штраф растёт с числом лишних элементов. `#IMAGE` засчитывается только при «Картинки: есть». Цитата
  засчитывается, только если она из Википедии: её текст (без учёта регистра, кавычек, пробелов и ё/е) найден
  в ответах инструментов этого эпизода; цитата, которой там нет, при поиске даёт −0,25 (решение 29.10.2026);
  многоточие в цитате — пропуск: части ищутся по порядку; без поиска цитаты не засчитываются (ни плюса, ни минуса).
  Неудачный график не засчитывается, но и не штрафуется: штраф сделал бы его хуже отсутствия визуала, и модель
  перестала бы рисовать графики, а в GRPO ответ без бонуса и так проигрывает ответу с хорошим графиком.
  Неудачный (`flat_plot`, решение 27.10.2026) — горизонтальная прямая (функция или все значения линейного `#CHART`
  постоянны); нелинейная функция, которая на выбранном отрезке выглядит прямой: в координатах рамки (обе оси
  растянуты на рамку, как рисует matplotlib) кривая отходит от прямой между своими концами меньше чем на 2% рамки —
  так одним правилом проверяются пологие, наклонные и крутые линии; выброс сжал кривую в линию: 90% точек занимают
  меньше 3% высоты рамки (`tan`, `1/x` около нуля, `exp(x)` на длинном отрезке). Прямая из линейной формулы (U = IR) —
  не ошибка: её отклонение от прямой нулевое, а не просто малое. Функция, не определённая больше чем на половине
  отрезка (`log(x)` на [−10; 1]), рисуется, но считается ошибкой (`undefined_plot`, −0,5, как `render_error`); если
  на отрезке нет ни одной точки — `render_error`. Проверку делает сборщик при отрисовке и пишет статус в отчёт. Риск бонуса — визуал «для галочки»: в набор испорченных
  презентаций входит бессодержательный визуал, награда за него не должна расти.
- Наполненность слайда (решение 27.10.2026). Отдельных штрафов за пустой слайд (только заголовок или заголовок
  с `#NOTES`), за слайд с одним коротким пунктом и за разделительный слайд («Часть 2. Причины») нет: такая
  презентация теряет в информации, и это уже снижает покрытие и ключи. Минимума слов на слайде нет. Избыток текста
  штрафуется только по факту сборщика — текст не поместился (`text_overflow`), а не по числу слов: подробный слайд
  лучше. Штраф — 0,1 за каждый такой слайд; включён после калибровки оценки по PowerPoint (раздел 3), до неё
  порог был завышен и наказывал нормальные слайды.
- Формат (решение 27.10.2026): штраф — доля битых строк `1 − parse_rate`; от длины ответа не зависит и мал намеренно:
  битая строка уже наказана косвенно (потерянный график снижает визуал, потерянный пункт — покрытие). Обрыв по лимиту
  токенов отдельно не штрафуется: цикл повтором слайдов ловит длина, повтором вызовов — штраф за повтор, мусор —
  `parse_rate`, повтор строк на слайде — `text_overflow`; отсутствие заключения снижает покрытие.
- Ошибки (решение 27.10.2026). Элемент, который сборщик не смог отрисовать (`render_error`), даёт −0,5 в визуальной
  сумме: ошибка в записи (LaTeX, выражение графика) исправима, а на слайде остаётся пустое место. Штраф меньше, чем
  за элемент сверх предела (−1), потому что есть риск, что модель перестанет рисовать графики и формулы; это
  проверяется на роллаутах. `#SOURCE` с id, которого не было в результатах инструментов эпизода (`bad_source`,
  выдуманный источник), — −0,1 за каждый. Заглушки в квадратных скобках («[Ваше имя]») отдельно не штрафуются.
- Повтор вызова инструмента (решение 27.10.2026). Повтор — тот же инструмент с тем же аргументом: для `search` —
  тот же набор слов запроса в начальной форме (регистр, порядок слов и падежи не важны), для `open` и `read` — тот же
  id; продолжение длинного раздела — не повтор. Перефразировка другими словами повтором не считается: её можно
  узнать только по результату, а модель не знает его заранее. Каждый повтор — штраф 0,1 сверх обычной стоимости
  вызова; повтор тратит вызов из лимита. Если вызов совпадает с прежним слово в слово, среда не выполняет его,
  а отвечает «Такой запрос уже был» (раздел 4).
- Ключи: тезис может занимать два слайда, поэтому `key` ищутся на двух лучших по `sim` слайдах; найденный ключ
  вычёркивается, каждый считается один раз. Поиск — с точностью до окончаний: ключ и текст слайда приводятся
  к начальной форме слов (лемматизатор для русского, например pymorphy3), без учёта регистра и ё/е; в датах
  и числах убираются «г.», «год», пробелы («6 400», «н. э.»). Ключи пишутся в начальной форме, а на слайде
  они в падежах и во множественном числе — дословный поиск их бы пропускал. Награда —
  доля найденных ключей; за содержание сверх ключей штрафа нет. Ключ засчитывается только на слайдах своего тезиса,
  поэтому список всех дат на одном слайде не помогает; вес ключей меньше веса покрытия; штраф KL держит текст
  у речи исходной модели. Это и компонент точности: неверный год вместо ключевого снижает награду.
- Порога «раскрыт / не раскрыт» нет: GRPO сравнивает ответы на одно задание между собой, эталон у них общий,
  и разный уровень сходства у разных составителей на сравнение не влияет. В сравнение идут только видимые элементы
  слайда: `#TITLE`, `#TEXT`, `#BULLET`, `#QUOTE`, подписи `#DIAGRAM`, `#TIMELINE` и `#CHART`, и только те, что
  сборщик нарисовал (без отброшенных из-за переполнения). Не идут `#NOTES`, `#IMAGE`, `#SOURCE`, `#PLAN` (иначе
  модель учится прятать содержание туда, где его не видно) и `#FORMULA` (эмбеддер плохо понимает LaTeX; формулы
  проверяются отдельно).
- Фоновое сходство: у эмбеддеров сходство постороннего текста не нулевое. В GRPO постоянная поправка на задание
  ничего не меняет (её убирает вычитание среднего по группе); в PPO её должен выучить критик, и вычитание фона
  тезиса (среднее `sim` со слайдами чужих тем, считается один раз до обучения) снимает с него лишний шум и делает
  числа сравнимыми между заданиями. Вводить ли — решается. Эмбеддер выбираем на роллаутах T-lite: кандидаты —
  `multilingual-e5-small` (на процессоре, префиксы `query:`/`passage:`) и `bge-m3`.
- Профили нормируются в [0, 1] по заранее зафиксированным шкалам, не по батчу.
- Перед RL награда проверяется на испорченных презентациях (решение 29.10.2026). Исходники — 16 ответов T-lite
  из EXP-010 и EXP-012 (по одному на тему validation с тезисами), исправленные вручную и дополненные слайдами
  до нижней границы ожидаемого диапазона (`data/perturbation/originals/`, правки — `edits.md`): в исходнике
  с ошибками искажение неоднозначно. Каждый компонент награды проверяется своим искажением:

  | Компонент | Искажение | Награда должна |
  |---|---|---|
  | покрытие | удалено объяснение тезиса | упасть |
  | покрытие | верный заголовок над пустым или чужим содержанием | упасть |
  | покрытие, ключи | вместо текста — голый список ключей | упасть |
  | покрытие | содержание перенесено в `#NOTES`, `#PLAN` или описание `#IMAGE` | упасть |
  | покрытие (заключение) | нет заключения; последним — обычный слайд вместо заключения | упасть |
  | ключи | неверный год или число из `key` | упасть |
  | длина | дубли слайдов, посторонние слайды | не вырасти |
  | длина | число слайдов задано в запросе, а слайдов меньше или больше | упасть |
  | визуал | убраны все визуальные элементы | упасть |
  | визуал | элементов одного типа сверх ⌈0,5·N⌉ (картинок — сверх N), всего сверх 2·N | не вырасти, при большом излишке упасть |
  | формулы | формул сверх 2·N | упасть |
  | сборщик | больше 2 крупных элементов или 3 формул на слайде | упасть |
  | ошибки отрисовки | битые данные `#CHART`, `#PLOT` с функцией, не определённой на отрезке | упасть |
  | ошибки отрисовки | `#PLOT` с постоянной функцией | не вырасти |
  | цитаты | цитата, которой нет в выдаче поиска | упасть |
  | картинки | `#IMAGE` при «Картинки: нет» | упасть |
  | источники | `#SOURCE` с несуществующим id | упасть |
  | формат | строки без тега (Markdown, обычный текст, ограждения кода) | упасть |
  | формат | опечатка в теге, неверный синтаксис элемента | упасть |
  | текст | текст не помещается в колонку | упасть |
  | инструменты | повтор вызова; лишние вызовы | упасть (лишние — немного) |
  | инструменты | вызов в режиме без поиска | упасть |
  | — | перефразировка, перестановка обычных слайдов | почти не измениться |

  Считается, во-первых, доля правильно упорядоченных пар по типам искажений (направление), во-вторых — награда
  с текущими коэффициентами (величина): средний сдвиг награды и каждого компонента по типам искажений
  в сравнении с естественным разбросом награды внутри задания (8 ответов T-lite на тему, EXP-010 и EXP-012) —
  штраф должен быть заметен на фоне этого разброса (иначе GRPO его не почувствует) и не перевешивать содержание
  (одна неудачная диаграмма не должна стоить больше, чем нераскрытый тезис). По этим двум анализам подбираются
  эмбеддер, α, λ, веса покрытия и ключей и проверяются коэффициенты штрафов. Неверные факты вне `key` — задача
  метрики точности (раздел 8), а не награды.
- Устройство проверки на искажениях (решение 01.11.2026).
  - Пары заморожены и не зависят от проверяемой награды: какой слайд какой тезис объясняет, где числовые ключи,
    какие слайды независимы (для перестановки), — ручная разметка исходников (`data/perturbation/annotations.json`);
    варианты генерируются один раз (`perturb.py`) и сохраняются целиком — текст DSL и манифест (исходник, тип
    и сила искажения, слайд, тезис, изменённые строки, предусловия, ожидание для целевого компонента и для всей
    награды). Атака на «лучший слайд по награде» — отдельное испытание с отдельным отчётом.
  - У искажения — предусловия (тезис не раскрыт на другом слайде, исходник в пределах лимита визуала и т. п.):
    вариант, где задуманный дефект не получился, отбрасывается до оценки, но никогда — потому что награда не упала.
  - Ожидания — числами, заранее, одни на все конфигурации: «упасть» — Δ ≤ −m, «не вырасти» — Δ ≤ ε, «почти
    не измениться» — |Δ| ≤ ε; m = 0,25·σ и ε = 0,1·σ, σ — медиана стандартного отклонения награды внутри
    задания по 8 ответам T-lite (EXP-010, EXP-012), считается для каждой конфигурации (пороги сравнимы при разных
    эмбеддерах), не меньше 0,005. Проверяются отдельно целевой компонент и вся награда; ничьи считаются отдельно.
  - Кроме искажений из таблицы: все тезисы на одном перегруженном слайде; объяснение тезиса, разделённое на два
    слайда; заголовок с формулировкой тезиса над пустым телом; нерелевантный, но нарисованный визуал в пределах
    лимитов; разбавление битых строк пустыми корректными; значения ровно на лимите и на единицу сверх; ключ
    в другой словоформе и другой записи числа; «Заключение» без выводов; важный текст после 512 токенов эмбеддера;
    цепочки «одна → несколько → много ошибок»; обратные пары — исправление должно повышать награду. Диагностика
    без подбора (фиксирует ограничение награды): отрицание, обмен субъекта и объекта, причина и следствие наоборот,
    неверные единицы.
  - Пары с конфликтом достоинств (полнее, но длиннее; перефразировка против перечня ключей и т. п.) — 30–50 пар:
    какая презентация лучше, решает Codex вслепую (случайный порядок, рубрика, без награды); часть пар размечает
    автор — для оценки согласия. По ним выбираются λ и соотношение покрытия и ключей: изолированные искажения
    определяют только знак.
  - Выбор конфигурации сетки — вложенная перекрёстная проверка по темам (исходник и все его варианты — в одной
    группе): 4 внешних разбиения, 3 внутренних; критерий зафиксирован до просмотра результатов — отсев конфигураций
    с провалами в семействах, затем средняя доля выполненных ожиданий по семействам (не по парам), при близких —
    устойчивая область. Отчёт — по семействам искажений и режимам поиска, медиана и среднее Δ, доля нарушений

    итог проверяется на новых темах (естественные группы ответов, best-of-N вслепую, короткий пилот RL).

    (или обрезанное до первого предложения, если чисел нет) против списка ключевых слов тезиса на том же слайде
    (вес ключей); презентации различаются только этим слайдом. Судья видит
    запрос, справку с проверенными числами темы (`data/perturbation/conflicts/facts.json`; другие факты
    не проверяет) и обе презентации текстом (видимые элементы, заметки, источники названиями) в случайном порядке;
    рубрика — без награды (`perturb.RUBRIC`).
- Изменения награды по итогам проверки на искажениях (решение 07.11.2026, EXP-014). Эмбеддер —
  bge-m3, α = 0,2. Остальное — кандидаты; каждое проверяется по отдельности и вместе (абляции) во втором прогоне.
  - Покрытие относительно фона: фон тезиса b — среднее по чужим презентациям (90 примеров SFT, их темы не входят
    в RL) максимума сходства тезиса с их слайдами по той же формуле sim (для тезиса-заключения — сходство
    с последним слайдом); покрытие тезиса = (sim − b)/(1 − b), без отсечения нулём (иначе плохо раскрытый тезис
    ничего не стоит и его выгодно выбросить). Фон считается один раз до обучения для каждого эмбеддера и α.
  - Ключ засчитывается только на слайде, где тезис раскрыт (сходство выше фона): лексическое совпадение уже входит
    в покрытие через α, и список ключевых слов не должен оплачиваться второй раз.
  - Числа и единицы в лемматизаторе: «N тысяч» → число, «миллион» = «млн», «миллиард» = «млрд», «₽», «руб.» → «рубль»,
    «%», «процентный» → «процент»; ключ с числом засчитывается только связкой «число + единица» подряд.
  - Числовое противоречие: если у ключа «число + единица» верной связки на слайдах тезиса нет, а та же единица стоит
    с другим числом, — штраф 0,05 за ключ. Голые числа (годы) так не проверяются — ограничение.
  - Прямые штрафы вместо долей суммы визуала: переполнение слайда, ошибка отрисовки (в том числе неопределённый
    график), формула сверх предела — по 0,05, выдуманная цитата — 0,1. Один элемент — один штраф по главной причине,
    за ненарисованный элемент бонуса нет.
  - Связь визуала со слайдом: текст визуала (описание картинки; узлы и подписи схемы; события хронологии; заголовок,
    категории и единица графика; заголовок и выражение графика функции) сравнивается с текстом слайда без заголовка
    (если текста нет — с заголовком); ниже порога τ — без бонуса и без штрафа; одинаковые элементы засчитываются один
    раз. τ для каждого вида визуала — по исходникам: положительные примеры — их визуал на своих слайдах, отрицательные —
    визуал близких чужих тем (тот же тип темы) на этих слайдах; τ — наибольший порог, при котором проходит не меньше
    95% положительных. Если положительных или отрицательных меньше 15 или отрицательных отсеивается меньше половины,
    вид визуала идёт без проверки за половину бонуса. Формулы и цитаты не проверяются (у цитат — своя проверка).
  - Второй прогон: те же правила выбора; варианты — исходная награда, каждое изменение по отдельности и все вместе
    (на bge-m3, α = 0,2), сетка λ × вес ключей — для полного варианта. Отчёт — Δ в абсолютных числах и в σ старой
    и новой награды, старый критерий (0,25σ старой) сохраняется для сравнения. Это регрессия, а не независимое
    подтверждение: изменения придуманы по этим парам; независимая проверка — на 4–6 новых исходниках из тем validation.
  - Реализация: каждое изменение — свой переключатель, по умолчанию выключен, и награда совпадает с прежней (проверено
    на всех 1099 вариантах). `RewardWeights`: `relative`, `keys_gate`, `contradiction`, `direct_penalties`
    (+ размеры штрафов), `visual_tau`, `visual_unverified`; `Lemmatizer(units=True)`; фон — `thesis_backgrounds`
    и `score(backgrounds=...)`. Фон считается с теми же α и лемматизатором, что и награда. Числовое противоречие
    ищется на двух слайдах тезиса независимо от фона (неверное число на слабом слайде — тоже противоречие);
    «единица» — существительное или слово вне словаря сразу после числа («8,5 %», «6 октября», «3,4 нм», «300 dpi»). Связь визуала со слайдом —
    косинус текста визуала и текста слайда (оба как passage). Пороги — `perturb_eval.calibrate_tau` по 16 исходникам;
    варианты абляций — `perturb_eval.VARIANTS`, прогон — `notebooks/reward_perturbations.ipynb` при `RUN = "ablation"`.
  - Новые исходники для независимой проверки — 4 темы validation (t366, t372, t376, t378; 254 пары),
    `data/perturbation/holdout` (правки — `holdout/originals/edits.md`); t383 и t385 не взяты: факты не проверить.
    Пороги m и ε — от σ основного набора; оценка — те же конфигурации, что во втором прогоне (последняя ячейка ноутбука).
  - Итог второго прогона и проверок (решение 07.11.2026, EXP-016). **Принято** (по умолчанию в `RewardWeights`
    и `Lemmatizer`): прямые штрафы (выдуманная цитата −3σ вместо −0,14σ, переполнение и ошибка отрисовки — во всех

    исходниках +0,30σ → −0,45σ; пороги — `rewards.VISUAL_TAU`: картинки 0,411, схемы 0,522 для bge-m3, остальные виды —
    за половину бонуса); числа и единицы (другая запись ключа сохраняет ключ в 78% пар вместо 44%). Повтор одинакового
    визуала — как элемент сверх предела (−1 в сумме; формула — как формула сверх предела): иначе копии не стоят
    ничего, и проверка «сверх предела» на копиях перестаёт работать (после EXP-016, отдельно не прогонялось).
    **Не принято** (переключатели выключены, оставлены для абляций): ключи только выше фона — эффекта нет, список ключей
    проходит фон (лазейка `keys_only` +0,16σ без изменений); покрытие относительно фона — падения покрытия сильнее
    на 20%, но σ растёт на 11%, а перефразировки на новых исходниках держатся хуже (0,90 → 0,70); числовое
    противоречие — на 320 ответах T-lite из 52 срабатываний настоящих ошибок 4, остальное — другие величины с той же
    единицей («снижение на 18%» против ключа «10%»), сужение (числа из ключей темы не считать) почти не помогло
    (37 → 34 ответа), неверных чисел в парах ловит 6 из 24. Веса прежние: λ = 1, ключи 0,5, визуал 0,2 — пары
    с конфликтом их не различают, а вес ключей 1 втрое усиливает лазейку `keys_only` и штраф за другую запись ключа.
    Ограничения награды: неверное число в ключе почти не наказывается; список ключей без объяснения не наказывается —
    в RL следить предполагалось за долей слайдов «почти одни ключи» — отменено 08.11.2026 (см. ниже).
    Уточнение 08.11.2026: рост награды у `keys_only` — в основном от **добавленных** ключей, а не от
    убранного объяснения. Искажение пишет на слайд все ключи тезиса, в том числе те, которых в исходнике не было
    (а модель списка ключей не знает). По EXP-016 (bge-m3, α = 0,2, вес ключей 0,5, σ = 0,084): в 39 парах из 44
    ключей стало больше — ключи +0,30σ, покрытие −0,10σ, награда +0,19σ (выросла в 34); в 5 парах ключей не прибавилось —
    награда −0,22σ (выросла в 1). То есть голый список сам по себе не выгоден; слабое место другое — убранное
    объяснение стоит покрытию всего −0,1σ.
    Решение 08.11.2026: признак «почти одни ключи» **не используем** — ни в награде, ни в журнале, ни при выборе
    чекпоинта. Он не показывает лазейку: слайд, где модель раскрыла все ключи, может быть хорошим, а надёжно отличить
    «голый список» от объяснения мы не умеем. Ключи в награде засчитываются как раньше. Защита от лазеек — выбор
    чекпоинта слепым судьёй, который награду не видит (раздел 9).
- Стоимость вызова при «Поиск: есть» — 0,003 за вызов (решение 08.11.2026; было 0,02, `RewardWeights.tool_call`).
  При 0,02 пять вызовов «поиск → оглавление → раздел» стоили около 1,4σ награды (σ — разброс внутри задания,
  EXP-016) — сравнимо с эффектом целых искажений, и RL мог научить модель не искать ради экономии на вызовах.
  0,003 оставляет только различие «при равном результате меньше вызовов лучше» (5 вызовов ≈ 0,2σ); от бессмысленных
  вызовов защищают штраф 0,1 за повтор и лимит вызовов. Штраф за вызов при «Поиск: нет» (0,1) не меняется.
  В проверке на искажениях (`perturb_eval.OLD`) для воспроизводимости EXP-014 и EXP-016 оставлено 0,02 (регрессия
  на 220 вариантах — без расхождений); вариант `accepted` — все принятые настройки по умолчанию, включая 0,003.
- Проверка веса ключей на принятой награде (08.11.2026, `notebooks/reward_keys_weight.ipynb` — копия
  `reward_perturbations.ipynb`, чтобы сравнить с прежним прогоном): вес ключей 0; 0,25; 0,5; 1 на варианте `accepted`,
  та же вложенная проверка, отложенные исходники и согласие с судьёй на парах о ключах (`keys_conflicts.csv`). Вопрос —
  не завышает ли вес 0,5 лазейку `keys_only` и штраф за другую запись ключа после принятых изменений.
  *Итог 10.11.2026 (EXP-018):* вес ключей 0,5 остаётся — выбран во всех блоках вложенной проверки, выбор устойчив
  и надёжен. Лазейка `keys_only` при 0,5 — +0,09σ / +0,17σ (ниже порога 0,25σ), убирает её только вес 0 ценой
  совпадения с судьёй на парах о ключах (7% против 79%); другая запись ключа не наказывается ни при каком весе.
- Длина вместо отдельного штрафа за повторы (решение 26.10.2026). Смысловое сравнение слайдов между собой
  (эмбеддинги, порог, калибровка) слишком дорого в разработке. Вместо него ожидаемый диапазон числа слайдов:
  если число задано в запросе — оно (`slide_range`), штраф за отклонение в обе стороны; если не задано — титульный +
  от C до ⌈1,3 · C⌉ содержательных + заключение, где C — число тезисов без заключения, штраф только за избыток
  (короткую презентацию наказывает покрытие). Штраф — расстояние до ближайшей границы, делённое на верхнюю границу;
  внутри диапазона нуля. Повторы этим ловятся косвенно: при числе слайдов около числа тезисов повторный слайд
  занимает место непокрытого тезиса и снижает покрытие. Множитель 1,3 оставляет мало места на дубли и покрывает
  разницу составителей (около 1–1,4 слайда на тезис). Вес λ подбирается на испорченных презентациях: дубли
  слайдов и превышение заданного числа — награда падает; длина внутри диапазона — не меняется.
- Веса компонентов подбираются на train/validation, не на test.

- Нижний порог награды в RL (решение 12.11.2026, EXP-019). Итоговая награда обрезается снизу на −1. Штрафы
  складываются без верхней границы, и отдельные ответы получают до −28,6; преимущество GRPO делится на разброс наград
  всего шага, поэтому один такой ответ сжимает преимущества остальных эпизодов в десятки раз. −1 — самый высокий
  порог, который не задевает ни одного задуманного одиночного штрафа (самый сильный — запрещённая картинка, около
  −0,8…−0,9; выдуманная цитата и чужой источник — −0,2…−0,25): обрезаются только сложенные «катастрофы», различать
  которые между собой незачем. Порядок обычных ответов не меняется; у исходной T-lite при T 0.9 ниже −1 — 1 ответ
  из 200, разброс шага в модели 2000 шагов почти не меняется (медиана 0,215 → 0,213). Компоненты в журнал пишутся
  без обрезки.

## 8. Метрики и итоговая оценка

- Автоматические метрики разбора, сборки и ограничений считаются на всех ответах.
- LLM-судья — только на validation и test, после сверки с ручной оценкой на небольшой выборке.
- Ручная оценка на test: шкала 0–4 по фактической корректности, глубине, ясности, структуре, визуальному качеству;
  покрытие каждого `key_point` — 0 / 1 / 2. Проверка вслепую, без названий моделей.
- Неизмеренное значение — `null`, а не ноль; рядом со средними публикуются знаменатели.

## 9. Обучение

- SFT: LoRA на все линейные слои (внимание и MLP), ранг 32–64, скорость обучения примерно в 10 раз
  выше, чем для полного дообучения; loss только по ответу. Основание — «LoRA Without Regret» (Thinking Machines, 2025):
  на небольших наборах SFT и в RL LoRA не уступает полному дообучению, если стоит на всех слоях; LoRA меньше забывает
  исходные знания (Biderman и др., 2024). QLoRA — только при нехватке памяти (Kaggle T4): адаптер, обученный поверх
  4-битной модели, при вливании в 16-битную даёт не ту модель, что обучали, и генерация в 4 битах медленнее.
  Сравнение «полное SFT против LoRA» на тех же 90 примерах — по желанию, если останется время (на 8×V100 помещается).
- SFT — устройство (решение 03.11.2026). Примеры (90 без поиска и 47 с поиском) собираются в токены той же функцией
  эпизода, что и роллауты (`environment.run_episode`; с поиском — `sft_search.replay`): шаблон чата — только для начала
  эпизода (системный промпт, инструменты, запрос), реплики модели и выдача — как их собирает среда (`subtleties.md`).
  Loss — только по репликам модели (маска эпизода); промпт и выдача Википедии в loss не входят. Вместо TRL `SFTTrainer` —
  `transformers.Trainer` с LoRA (peft): `SFTTrainer` сам токенизирует и применяет шаблон чата, что ломает совпадение
  с роллаутами, и меняет интерфейс между версиями; логиты считаются только в позициях с меткой (иначе логиты на всю
  длину эпизода при словаре ~150 тыс. не помещаются в память V100). LoRA: ранг 32, α = 32, без dropout, все линейные
  слои; скорость 2·10⁻⁴, косинусное расписание, разогрев 3%; батч 1, накопление 8; 3 эпохи; float16 и чекпоинтинг
  градиентов. Отложено 9 тем SFT (все их примеры) — по loss на них выбирается эпоха. Главная проверка — генерация
  на 25 темах validation в обоих режимах против исходной T-lite (формат, слайды, заключение, поиск, `#SOURCE`), EXP-015.
- Приёмка SFT (решение 07.11.2026, до проверки генерацией; EXP-015). Сравнение с исходной T-lite на 25 темах
  validation в обоих режимах, по одному ответу на тему и режим с одинаковым seed, разница по парам тем с 95%
  интервалом бутстрепа; «хуже» и «лучше» — интервал целиком по одну сторону от нуля. SFT принимается, если он:
  не хуже по доле корректных строк и по `#SOURCE` не из выдачи; лучше хотя бы по одному из — заключение последним
  слайдом, число слайдов в ожидаемом диапазоне, вызов поиска при «Поиск: есть»; не хуже по награде; разброс награды
  внутри темы (4 ответа без поиска, 6 тем) сузился не больше чем вдвое. Запросы к Википедии и картинки считаются
  и показываются, но в правило приёмки не входят.
- Reference для RL: SFT-адаптер сливается с базой во float16 (V100 не поддерживает bfloat16), поверх учится новый LoRA
  (окончательно — на шаге `training/common.py`).
- PPO и GRPO пишем сами на общей основе `training/common.py`; сначала GRPO, затем PPO (критик, GAE).
- Rollout'ы генерируются с температурой 0.9, без top-p/top-k и штрафа за повторы; log-prob в обучении
  считаются при той же температуре. Рекомендованные параметры модели используются только на инференсе.
- Настройки генерации по умолчанию (найдено 08.11.2026): `generation_config.json` T-lite задаёт
  T = 0,7, top-p 0,8, **top-k 20**. `model_loader.hf_generator` переопределяет температуру и top-p, но не top-k —
  поэтому ответы EXP-010, EXP-012 и пробные ответы EXP-015 сгенерированы с top-k 20 (T = 0,9, top-p 1). В RL все
  параметры выборки задаются явно: T = 0,9, top-p 1, top-k выключен (`transformers`: 0, vLLM: −1), штрафы
  за повторы и присутствие — нейтральные; иначе генерация и формула вероятностей при обучении — разные распределения.
  Исправлено 08.11.2026: `hf_generator(..., top_k=0)` и `repetition_penalty=1.0` явно. Без top-k уже проверяли:
  в EXP-003/EXP-004 он был выключен явно (`top_k=0`) — исходная T-lite при T = 1 вырождалась в 4 ответах из 24, при
  T = 0.9 — ни разу; позже написанный генератор эту настройку потерял. Проверка после SFT (EXP-017, правило до запуска):
  SFT-модель, 10 тем × 4 ответа без поиска, top-k 0 и 20; top-k 0 остаётся, если вырожденных ответов при нём не больше,
  чем при top-k 20, плюс 2 из 40, и средняя награда ниже не больше чем на 0,25σ. Иначе — T = 0.8 без top-k
  (запасной вариант EXP-004; вариант с top-k 20 убран, см. ниже). Дополнено 11.11.2026 до запуска
  проверки: те же 10 тем × 2 ответа с поиском (Википедия на сервере открыта; в RL половина эпизодов с поиском, длинная
  выдача — отдельный риск вырождения); правило — в каждом режиме отдельно, допуск +2 из 40 без поиска и из 20 с поиском;
  не проходит хотя бы один режим — T = 0.8 без top-k. Итог 11.11.2026: top-k 0 не прошёл в обоих режимах по награде (без
  поиска −0,62 при пороге −0,02; с поиском −0,10), по вырождению — в допуске; дальше T = 0.8 — в EXP-019.
- Старт RL (решение 11.11.2026, до прогона EXP-019). Адаптер эпохи 3 из 7 не прошёл приёмку SFT (EXP-015: награда
  ниже исходной T-lite в обоих режимах, `#SOURCE` не из выдачи чаще; петли в 13 ответах из 90). Сетка: исходная T-lite,
  адаптеры эпохи 3 из 7 и эпохи 3 из 3 × T 0.8 и 0.9, 25 тем × 2 режима × 4 ответа, генерация через vLLM. Допуск
  против исходной T-lite при той же температуре: правило приёмки SFT (07.11.2026), разница — средних по 4 ответам темы,
  бутстреп по темам; плюс доля вырожденных ответов (признаки EXP-017) — не больше, чем у исходной, плюс 5 п.п. (10 ответов из 200;
  как +2 из 40 в EXP-017) Выбор
  среди допущенных: меньшая доля вырожденных; если у нескольких она в пределах 2 п.п. от лучшей — большая средняя
  награда. Победитель задаёт и адаптер (опорную модель RL), и температуру RL. Если не допущена ни одна — решаю после
  прогона (варианты: RL с исходной T-lite или с лучшим адаптером с записью об отступлении от правила). Итог 12.11.2026:
  не допущена ни одна конфигурация (вырожденных 12–18,5% против 1–1,5%, награда ниже в обоих режимах). Старт RL
  остаётся с SFT-адаптера: SFT переобучается — данные и скорость (EXP-020), проверка тем же правилом. Если и новый
  адаптер не пройдёт — RL с лучшим адаптером с записью об отступлении от правила. Выбор SFT-адаптера (по loss на отложенных примерах, teacher forcing) от параметров выборки не зависит.
- KL-штраф (решение 08.11.2026): β фиксированный, 0,02, одинаковый для GRPO и PPO; оценка в loss — k2, в журнал — k3.
  Адаптивный β (держит KL у цели) — только абляцией, если KL уйдёт слишком далеко: при адаптивном β регуляризация
  у двух алгоритмов была бы разной, и разница результатов смешалась бы с ней.
- Согласие награды с судьёй по ходу RL (решение 08.11.2026): на validation, не на test (test трогаем один раз,
  в конце); на каждом сохранённом чекпоинте (раз в 10 шагов) — 8 тем × 2 режима, по 2 ответа на задание (те же
  ответы, что для выбора чекпоинта); судья вслепую в двух порядках выбирает лучший; согласие — доля пар, где он
  выбрал тот же ответ, что награда; пары с разницей награды меньше 0,1σ не считаются. 32 вызова на чекпоинт, около
  480 на запуск (около 3 тыс. на 3 сида × GRPO и PPO, плюс итоговая оценка). Падение согласия при росте награды —
  признак лазеек. Судья выбирается заново с учётом этого объёма: кандидаты проверяются на согласие с моей
  разметкой (пары EXP-013), независимость от Qwen, русский язык, лимиты и стоимость.
- Чекпоинты RL: адаптер сохраняется каждые 10 шагов и хранится весь запуск (все кандидаты для проверки и выбора);
  полное состояние для продолжения (оптимизатор, сиды, шаг) — только для двух последних.
- Движок генерации для RL (решение 08.11.2026). Поштучная генерация (~13 токенов/с, ~90 с
  на эпизод) для шага GRPO в 64 эпизода слишком медленна. Сначала — **vLLM 0.8.5** в отдельном виртуальном окружении:
  последняя версия с официальной поддержкой V100; Python 3.10–3.11, PyTorch 2.6.0, xformers 0.0.29.post2,
  transformers 4.51.3, старый движок (`VLLM_USE_V1=0`), внимание xformers, веса float16, LoRA (ранг до 32).
  Ограничение на V100: нет кеширования общего префикса между запросами — после вызова инструмента контекст
  прогоняется заново. Новый LoRA после шага сохраняется в новую папку и подгружается под новым номером, старый
  выгружается. Пробный запуск удачен, если: (1) vLLM ставится и грузит T-lite во float16; (2) подгружает и меняет
  LoRA без перезапуска; (3) на 64 эпизодах быстрее поштучной генерации хотя бы в 3–4 раза; (4) вероятности токенов
  vLLM совпадают с `transformers` в пределах погрешности float16. Иначе — пакетная генерация в `transformers` (группа
  одним пакетом: «до вызова → вызовы → продолжение»), про запас — форк 1Cat-vLLM. Скорость замеряется у всех
  опробованных способов (поштучно / пакетно / vLLM) — это результат для текста работы.
- Опорная модель и старт RL (уточнение 08.11.2026). SFT-адаптер вливается в базу с вычислением во float32,
  результат сохраняется во float16; исходный SFT-адаптер хранится. Новый LoRA: ранг 32, все линейные слои, без
  dropout, в начале даёт нулевую поправку. Опорные вероятности — той же моделью под `no_grad` и
  `model.disable_adapter()`: второй копии весов нет, но нужен лишний прямой проход. Токенизатор, шаблон, служебные
  токены и температура у политики и опорной модели одинаковы. Проверки до RL: на старте вероятности политики
  и опорной модели совпадают в пределах погрешности, KL ≈ 0; слитая модель отвечает как SFT-модель с адаптером.
- Шаг GRPO (решение 08.11.2026): 8 заданий × 8 ответов = 64 эпизода; в каждом шаге 4 задания с поиском и 4 без
  (режим общий для группы). 64 эпизода — это 8 независимых тем, а не 64. Возможная абляция — 16 заданий × 4 ответа
  при том же числе эпизодов.
  Эпоха по заданиям — 548 заданий (274 темы × 2 режима): 68 полных шагов и один неполный (2 + 2 задания,
  32 эпизода); все формулы — по фактическому числу эпизодов шага (решение 08.11.2026).
- Нехватка памяти при обучении (решение 08.11.2026): эпизод **не пропускается** — иначе систематически
  выпадали бы длинные эпизоды (в основном с поиском) и в градиентах оставалась бы часть сбойного эпизода. Обновление
  не делается, накопленные градиенты очищаются, тот же пакет пересчитывается с заранее проверенной экономной
  настройкой, не меняющей математику (меньше кусок логитов; сохранённые активации чекпоинтинга — в память CPU).
  Не помогло — запуск останавливается; уменьшение предела длины — новая конфигурация для обоих алгоритмов.
- Расхождение вероятностей vLLM и обучающего прохода (решение 08.11.2026): vLLM 0.8.5 возвращает
  log p после деления на температуру — сравнение с `log_softmax(logits.float() / T)` на тех же токенах. Порог
  (среднее и 99-й процентиль |Δ log p| на токен) задаётся по пилоту vLLM до основных запусков; превышение на шаге —
  остановка запуска для разбора: обучение на данных не той политики нарушает предпосылку on-policy.
- Запасной путь при провале EXP-017 — только T = 0.8 без top-k (выбирается до основных запусков, одинаково для GRPO
  и PPO). Top-k 20 с урезанным распределением в обучении убран из запасных: выбранного политикой
  токена может не быть в top-k опорной модели (бесконечный log-ratio), а с полнословарной опорной моделью оценка KL
  некорректна; движки по-разному решают границу top-k. Также явно: `min_p = 0`, штрафы присутствия и частоты 0.
- Независимая метрика качества по ходу RL (предварительно, 08.11.2026, ещё обсуждаем): доля побед текущего чекпоинта
  над SFT-моделью у слепого судьи на тех же заданиях validation, пары не отбираются по награде. Согласие награды
  с судьёй измеряет надёжность награды, а не качество модели. Судью для этого ещё ищем.
- Опора на прочитанное (решение 08.11.2026, только аналитика — не награда и не выбор чекпоинта): в эпизодах
  с поиском — доля чисел и имён со слайдов, которые встречаются в выдаче инструментов, фактически показанной модели
  (после всех обрезаний). Числа и имена — то, что можно сверить буквально; пересказ так не сверить. Доля по эпизоду:
  найденные / все числа и имена на его слайдах; эпизоды без чисел и имён не входят в среднее, их число пишется
  отдельно. Рядом — доля слайдов со ссылкой (#SOURCE) на прочитанное. Ограничение (в тексте работы): совпадение
  числа или имени с источником не доказывает, что утверждение верно.
- **Полная спецификация GRPO — `docs/grpo.md`** (08.11.2026): параметры
  с обоснованием и текст для статьи. Ключевое: 150 шагов сбора = 9536 эпизодов; предел контекста — 25 тыс., если
  пройдёт проверку памяти, иначе меньше (запасной путь — уменьшение контекста); судья — асинхронный процесс по ответам
  validation каждые 10 шагов: (а) доля побед над SFT, (б) согласие награды с судьёй (только сигнал); кривые — по ходу
  обучения. **Ранней остановки нет** (решение 08.11.2026): все запуски ровно 150 шагов — чекпоинты сохраняются все,
  лучший выбирается после запуска, а остановка сэкономила бы только время ценой порогов, риска оборвать запуск
  на временной просадке и неравной длины запусков; явно сломанный запуск могу остановить вручную. Выбор —
  3 лучших по (а) → полный validation против SFT; доля побед ≤ 50% — итог SFT. Признаков лазеек и вето нет.
- Остановка: плато качества на validation по независимой метрике, но не дольше общего предела.
- Сравниваем: исходная модель, только SFT, SFT+PPO, SFT+GRPO — от копий одного SFT-чекпоинта.
- Сравнение GRPO и PPO — в их собственных конфигурациях (решение 08.11.2026, согласовано с научным руководителем):
  условия эксперимента одинаковые (задания, награда, среда, модель, SFT-старт, бюджет шагов, железо), а параметры
  обучения у каждого алгоритма свои — у GRPO одно обновление на пакет (μ = 1, как в DeepSeekMath), у PPO несколько
  (2–4, выбирается при проектировании PPO). Все различия конфигураций — в итоговой сравнительной таблице со ссылками;
  описываются как реализованные в работе, а не «алгоритмы вообще». Сиды: по 2 на алгоритм (4 основных запуска).
  Абляции (16 × 4, адаптивный β, PPO с μ = 1 и др.) пока не планируем — только если останется время.
- Показываем итоговое качество на test и кривые обучения относительно сгенерированных токенов и времени.
- Эффективность алгоритмов сравниваем только на одном и том же железе; остальные замеры подписываем устройством.

## 11. Код и инфраструктура

- Эталонные функции живут только в модулях `src/`; ноутбуки импортируют их для экспериментов и Kaggle.
- Код пишется по одному модулю: модуль + тест + ручная проверка результата.
- Git + приватный репозиторий GitHub — единственный источник кода; Kaggle и сервер берут код оттуда.
- Устройство выбирается автоматически: CUDA → XPU → CPU, с возможностью указать вручную;
  тип чисел — bf16 при поддержке, иначе fp16/fp32.
- Профили запуска: `local` (GTX 1660 Super, 6 ГБ), `server` (университетский, общий: 8×V100 32 ГБ, карты делятся
  между пользователями; диск 50 ГБ, квоту можно расширить), `kaggle` (T4, 16 ГБ).
- На диске сервера храним адаптеры LoRA (десятки МБ), а не слитые модели (по 16 ГБ каждая); веса базовой модели —
  один раз в кэше Hugging Face. Адаптер вливается при загрузке.
- Первый запуск на сервере — пробный прогон T-lite во float16 (`notebooks/tlite_episode_pilot.ipynb`), затем шаг LoRA.
- Правила общего сервера (очереди задач и лимита времени нет): перед запуском — `nvidia-smi` и закрепление свободных
  карт (`CUDA_VISIBLE_DEVICES`); обучение — скриптом в фоне (`tmux` или `nohup`, лог в файл), а не в тетрадке:
  ядро Jupyter и SSH-сессия умирают при обрыве связи; частые чекпоинты с продолжением; обучение работает на одной
  карте, несколько карт только ускоряют; скорость алгоритмов сравниваем в токенах и шагах, время подписываем загрузкой
  сервера; токены доступа — только в переменных окружения; кэш Hugging Face — вне домашней папки, если есть место
  без квоты (`HF_HOME`).
- Метаданные каждого запуска: хеш коммита, версия сохранённых ответов Википедии, устройство, тип чисел, версии библиотек, seed.
- Долгие запуски переживают обрыв связи и возобновляются с чекпоинта
  (LoRA, оптимизатор, scheduler, RNG, позиция в данных, шаг, критик PPO).
