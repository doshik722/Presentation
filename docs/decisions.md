# Принятые решения

Состояние на 29 сентября 2026 года. Если решение меняется, правим этот файл
и кратко записываем причину в раздел «История изменений».

## 1. Рамка работы

Работа одна — диплом. Он состоит из двух частей:

1. **RL-часть** (защищается как курсовая): агенты PPO и GRPO, обученные создавать презентации.
2. **LangChain-часть** (позже): агент на LangChain с теми же инструментами, сравнение с RL-агентами.

Исследовательские вопросы:

- как PPO и GRPO различаются по глубине итоговых презентаций и по эффективности обучения;
- насколько рационально давать агенту доступ к внешним источникам: один и тот же агент с поиском и без поиска
  (агент решает, что и когда искать, поиск выполняет среда);
- (диплом) чем RL-агенты отличаются от LangChain-агента при одинаковых инструментах и источниках.

## 2. Формат вывода модели — построчный DSL

Модель пишет весь текст сама, включая теги. Одна строка — один элемент: `#ТЕГ: значение`.

| Тег | Значение | Что делает сборщик |
|---|---|---|
| `#PLAN` | черновой план | пропускает |
| `#SLIDE` | без значения, начинает новый слайд | — |
| `#TITLE` | заголовок слайда | поле заголовка |
| `#TEXT` | абзац связного текста | абзац без маркера |
| `#BULLET` | пункт списка (только для настоящих перечислений) | пункт списка |
| `#FORMULA` | LaTeX (подмножество matplotlib mathtext) | PNG |
| `#CHART` | `type=bar\|line\|pie; title=...; x=...; y=...` | нативный редактируемый график pptx |
| `#PLOT` | функция и диапазон, например `y = x^2; x=-2..5` | PNG через matplotlib |
| `#DIAGRAM` | структура схемы текстом | PNG |
| `#TIMELINE` | `год — событие; год — событие` | фигуры на слайде |
| `#QUOTE` | цитата с атрибуцией | блок цитаты |
| `#IMAGE` | описание нужной картинки; только если в запросе «Картинки: есть» | картинка из Wikimedia Commons с подписью и лицензией |
| `#SOURCE` | id раздела из выдачи этого эпизода | ссылка на источник |
| `#NOTES` | заметки докладчика | заметки слайда |

Принципы:

- каждая строка разбирается независимо; битая строка теряется сама, остальные собираются;
- строки без тега и неизвестные теги считаются ошибками разбора, но не ломают презентацию;
- `parse_rate` — диагностика и небольшой компонент награды, не главный сигнал;
- модель не видит ни картинок, ни URL; она решает, что показать, а исполняет сборщик.

Точная грамматика (экранирование, числа, пустые значения, восстановление после структурных ошибок)
описывается отдельно в `docs/dsl_spec.md` до написания парсера.

## 3. Сборщик презентации

- Один сборщик для всех моделей и агентов; он не исправляет содержание и не переставляет слайды.
- Размеры шрифтов фиксированы: заголовок 30 pt, текст и цитата 20 pt, подписи 12 pt, источники 10 pt;
  подбирается только размер подписи внутри узла схемы (14–10 pt). Шрифт не уменьшается:
  не поместившийся текст отмечается в отчёте как `text_overflow` и учитывается наградой.
- Макеты: «текст», «текст + 1 визуальный элемент», «текст + 2 визуальных элемента».
- Картинки: сборщик по описанию из `#IMAGE` ищет кандидатов в Wikimedia Commons и выбирает через мультиязычный CLIP;
  модель картинок не видит и не выбирает (решение 01.10.2026). Для скачивания сборщику нужен интернет; если его нет,
  ставится заглушка и запись в отчёте — это сбой окружения, а не ошибка модели. При обучении картинки не скачиваются.
- Отчёт сборщика фиксирует, какие элементы не удалось отрисовать и почему.
- Палитры (`rendering/themes.py`): 6 палитр с проверенной контрастностью текста (WCAG: основной текст ≥ 7,
  подписи ≥ 4,5). Различаются только цвета; шрифты, размеры и раскладка общие, поэтому палитра не влияет
  на заполнение и переполнение. Модель палитру не выбирает и не видит; пользователь задаёт её полем
  `theme` в запросе, по умолчанию (`auto`) палитра выбирается по тексту запроса — один запрос всегда получает
  одну палитру, разные запросы — разные.

## 4. Эпизод и агент

Для пользователя презентация создаётся за одну генерацию; внутри неё модель может обращаться к поиску.

**Один агент; поиск и картинки — два независимых поля запроса** (решение 15.10.2026, вместо отдельных этапов A и B).
Модель видит строки «Поиск: есть / нет» и «Картинки: есть / нет» и должна уметь работать при любом их сочетании.

- «Поиск: есть» — модель может вызывать поиск по Википедии и сама решает, обращаться ли к нему, что искать
  и что взять из найденного; сам поиск выполняет среда — всегда через живой API Википедии с сохранением ответов
  (раздел 5); интерфейс инструментов один и тот же при обучении, оценке и использовании.
  «Поиск: нет» — инструментов нет.
- Промпт по режимам (решение 20.10.2026): с поиском — начало «сначала найди факты в Википедии, потом пиши
  презентацию», поиск в промпте подчёркивается; без поиска — «сразу пиши презентацию», поиск и инструменты
  не упоминаются (описаний инструментов шаблон чата в этом режиме и так не получает). Вызов в режиме без поиска:
  при обучении не запрещается, а штрафуется наградой; при использовании запрещён — генерации запрещено выбирать
  токен `<tool_call>` (подробно — `docs/subtleties.md`). Формулировки — `prompts.py`: без поиска — вариант B
  из EXP-008, с поиском — вариант F из EXP-009 (вызов инструмента описан в разделе «Формат», пример — эпизод
  с вызовами) и правила «не повторяй запрос с мелкими изменениями, не читай раздел дважды».
- «Картинки: есть» — модель может писать `#IMAGE`, картинку ищет сборщик. «Картинки: нет» — `#IMAGE` не используется,
  вместо картинок — графики, диаграммы, схемы; `#IMAGE` при «Картинки: нет» не рисуется, не считается визуалом
  и штрафуется.
- Источники на слайдах — по желанию пользователя (поле `sources`, по умолчанию показывать). Модели это поле
  не передаётся: при поиске она всегда пишет `#SOURCE`, а убирает их со слайдов сборщик (`show_sources=False`);
  id при этом всё равно проверяются и сохраняются в отчёте — по ним видно, откуда взят материал.
- Язык презентации — русский, если в запросе не сказано иное. Английские термины там, где они приняты в теме,
  допустимы; проверяется язык основного текста, а не отдельные слова.
- Заранее, без запроса модели, среда ничего не ищет и в промпт не подставляет.
- Все сочетания — у одной обученной модели; сравнение «с поиском / без поиска» отвечает на вопрос о доступе
  к источникам (раздел 1).

- Во время генерации модель может вызвать инструмент: генерация останавливается, система выполняет вызов,
  дописывает результат в контекст, модель продолжает с того же места. Формат — шаблон чата T-lite-it-2.1 (как у Qwen3,
  сохранён в `configs/models/tlite_21_chat_template.txt`): модель пишет `<tool_call>{"name": …, "arguments": {…}}</tool_call>`
  и заканчивает реплику; среда выполняет все вызовы реплики и дописывает реплику user с блоками `<tool_response>`,
  затем новую реплику assistant с пустым блоком рассуждений (`<think>\n\n</think>`, как `add_generation_prompt`
  шаблона: режим рассуждений не используем). Реализация — `environment.py` (`run_episode`).
- Эпизод собирается по ходу генерации и не пересобирается шаблоном чата: шаблон ставит пустой `<think>` только
  у последней реплики, и пересборка дала бы текст, которого модель не видела (подробно — `docs/subtleties.md`).
  Примеры SFT с поиском составляются той же функцией эпизода.
- Эпизод хранится токенами, а не текстом (логарифмы вероятностей в RL — по тем же токенам, что сгенерированы);
  куски помечены «модель» / «инструмент и разметка», отсюда маска loss. Генерация передаётся функцией, среда от неё
  не зависит. Неразобранный вызов (не JSON, неизвестный инструмент, незакрытый тег) получает ответ с ошибкой и тратит
  вызов из лимита. Без поиска вызовы не выполняются: текст идёт парсеру и становится ошибкой разбора.
- Инструменты модели: `search`, `open`, `read` — в штатном формате вызова инструментов модели (решение 16.10.2026).
  Поиск, как и у Википедии, — по статьям; дальше модель сама открывает статью и выбирает раздел.
  Текст из разных мест не склеивается:
  - `search(запрос)` — до 3 статей из поиска Википедии на языке запроса (язык — по алфавиту, см. раздел 5)
    и до 3 их версий на другом языке; страницы значений пропускаются. По каждой — id статьи (`d3`), язык,
    название и первые ~200 символов введения. В описании инструмента: запрос — 1–4 ключевых слова, а не фраза
    (поиск Википедии длинные фразы понимает плохо);
  - `open(id статьи)` — введение и полное оглавление статьи (все уровни, id разделов вида `d3#5`) с подводками
    разделов, у которых есть подразделы (подводка — текст между заголовком и первым подразделом). Лимит 6000 символов:
    заголовки показываются всегда; если введение и подводки не помещаются, обрезаются только самые длинные —
    до наибольшего порога, при котором всё помещается (на пилоте введение и оглавление без подводок помещаются
    в 99% статей; что-то из подводок обрезается в 16% русских и 28% английских статей с подразделами);
  - `read(id раздела)` — текст одного раздела без подразделов (у раздела с подразделами — его подводка); лимит
    6000 символов (целиком помещаются 94% русских и 95% английских разделов), длинный обрезается по границе абзаца
    с пометкой «обрезано, ещё N символов».
  - Текст разделов — простой текст API Википедии; таблиц в нём нет, поэтому таблицы (`wikitable`) и карточка статьи
    (infobox) берутся из HTML той же правки и дописываются в конец своего раздела: «Таблица: подпись», строки ячеек
    через « | »; карточка — «Карточка статьи:», «поле: значение», в конце введения (`tools/wiki_tables.py`,
    решение 20.10.2026).
- Id живут только внутри эпизода (эпизод — один прогон модели на одном задании): статьи нумеруются `d1`, `d2`…
  по порядку появления, номер раздела — его порядковый номер в статье. Среда хранит таблицу «id → язык, номер
  страницы Википедии», в конце эпизода она пишется в лог вместе с ответом.
- Оглавление основной статьи в промпт **не даём**: модель получает его только по своему вызову `open`.
  Риск, что модель станет перекладывать оглавление Википедии в слайды, отслеживаем метрикой анализа
  (совпадение порядка слайдов с оглавлением); тезисы test из оглавления не копируются.
- Картинки — не инструмент модели: модель пишет описание в `#IMAGE`, ищет и выбирает картинку сборщик
  (Wikimedia Commons + CLIP). Если смотреть на систему целиком, это исполнительный инструмент:
  модель объявляет, что нужно, система выполняет после генерации; модель результата не видит.
- Вызов возможен в любом месте генерации. Парсер получает всё, что написала модель, по порядку,
  без блоков вызовов и результатов; план перед вызовом пишется тегом `#PLAN`.
- `#SOURCE` содержит id из этого эпизода: `d3` — статья из выдачи `search`, `d3#5` — раздел (`d3#0` — введение)
  открытой статьи; ссылку и оформление источников делает сборщик.
- Лимиты: 8–10 вызовов (точное число — по пилоту, с учётом длины контекста на V100), ограничение объёма
  прочитанного текста, небольшая стоимость каждого вызова. При трёх шагах «поиск → оглавление → раздел» 5 вызовов
  хватает только на один-два раздела.
- Для RL это многошаговый эпизод: результаты инструментов написаны не моделью и исключаются из loss маской.
- Перед вызовом модель может коротко написать план или причину выбора (`#PLAN`), но не обязана: T-lite не обучена
  режиму рассуждений, заставлять её не будем. Отдельной абляции «с мыслью / без мысли» нет.
  Длина текста между вызовами ограничена техническим лимитом токенов, без штрафа в награде.
- Среда и цикл генерации пишутся с поддержкой вызовов инструментов; ответ без вызовов — частный случай.

Многошаговое редактирование уже готовых слайдов отложено.

## 5. Источники

- Поиск — **живой API Википедии с сохранением ответов** (решение 16.10.2026, вместо заранее собранного корпуса):
  модель и при обучении, и при оценке, и при использовании получает настоящую выдачу Википедии. Каждый ответ API
  (выдача поиска, статья по разделам, межъязыковые ссылки) сохраняется и повторно не запрашивается: роллауты GRPO
  повторяют задания и запросы, так что большая часть вызовов берётся из сохранённого. Сохранённое фиксирует
  состояние Википедии: повторные прогоны и сравнения (test, LangChain-агент) идут по тем же ответам, новые запросы
  дописываются. Статьи хранятся по разделам с id ревизии и датой; метаданные картинок берутся из тех же статей.
- Язык поиска — по алфавиту запроса: есть кириллица — русская Википедия, иначе английская. Модель сама решает,
  на каком языке искать (для технических тем английская Википедия часто полнее); в примерах SFT с поиском
  составители иногда пишут запросы на английском.
- Выдача `search`: до 3 статей из поиска на языке запроса и их версии на другом языке по межъязыковым ссылкам,
  язык помечен (раздел 4). Своего ранжирования у нас нет: порядок статей — как у Википедии, раздел выбирает модель.
- Запросы к API — по одному, с паузой 0,5 с, контактом в User-Agent и повтором при перегрузке; при параллельных
  роллаутах — общая очередь. Промах стоит 1–2 с — мало по сравнению с генерацией (порядка минуты на ответ на V100).
  Сервер выходит в интернет (проверено 16.10.2026).
- Хранилище сохранённых ответов: приватный датасет Kaggle с версиями; на сервере — локальные файлы.
  Ответы пилота (`data/sources/wiki_pilot/`) переносятся в него.
- LangChain-агент получает те же инструменты, те же сохранённые ответы и те же лимиты.
- Сохранённые ответы не кладём в git. Тексты Википедии — CC BY-SA: при публикации указываем авторство и ту же лицензию.

## 6. Задания и данные

Запрос пользователя — `PresentationRequest` (`src/presentation_rl/tasks.py`): текст запроса и необязательные поля
`audience` (нет — модель выбирает сама), `slides` (число или диапазон), `domain` (`technical` / `humanities` / `auto`,
по умолчанию `auto`), `search` и `images` (по умолчанию включены; пользователь может выключить). Модель получает
текст запроса и заполненные поля.

- Число слайдов: если оно задано полем или в тексте («на 7 слайдов», «5–7 слайдов», «для слайда», «15 страниц»),
  требование берётся оттуда; если поле и текст противоречат друг другу, решает поле. Больше 30 не бывает (лимит
  парсера; просьба больше 30 урезается до 30). Не задано нигде — требования нет, модель выбирает число слайдов сама.
- Задание набора (`Task`, `data/tasks/tasks.json`) — запрос плюс сведения для выборок и отчёта: `split`, `source`,
  `family`, `scenario`, `discipline`, `has_course`, `has_material`. Темы из рабочих программ подаются как
  «Сделай презентацию на тему «…»» с аудиторией и типом темы; запросы WildChat и составленные — текстом пользователя,
  тип темы `auto`. `load_tasks` проверяет набор: уникальные id, одно семейство — одна выборка, непустой текст,
  допустимое число слайдов.
- Тезисы (`key_points`) хранятся отдельно от заданий.

- `domain` определяется по природе темы: `technical` — понятия, законы, модели, методы (инфляция — сюда);
  `humanities` — события, процессы и идеи в истории. Модели передаётся как подсказка, не как требование
  (награда на тип не смотрит): в технической теме обычно важнее механизмы, формулы и графики, в гуманитарной —
  события, причины и следствия, ленты времени и цитаты; это объяснение есть в промпте составителей и будет
  в системном промпте модели. По `domain` делим выборки
  и показываем метрики по типам.
- `key_points` и `expected_elements` модель **не видит**; их использует только оценка.
- Источники заданий (под наличие хороших статей Википедии темы не подбираются; если в Википедии мало материала,
  это часть задачи агента):
  - учебные темы из рабочих программ дисциплин российских вузов: 36 дисциплин поровну по типам, 72 программы,
    837 сырых тем (`data/tasks/raw_topics.json`, ссылки на документы — `raw_topics.md`);
  - реальные запросы пользователей из WildChat-1M (ODC-BY): русские диалоги с просьбой о презентации,
    отбор — `data/tasks/wildchat_requests.xlsx`, столбец «Беру»;
  - составленные запросы для сценариев, редких в WildChat (быт, научпоп, рабочие отчёты с данными):
    в таблице с id `автор` или `составлено`; в работе указывается их число отдельно от реальных.
  Отобрано из запросов 294: учёба 213, работа 35, быт 33, научпоп 9, другое 4. Берутся все; из рабочих программ —
  155 тем, в среднем по 4 на дисциплину, равномерно по курсу (`data/tasks/syllabus_topics.xlsx`: 674 очищенные темы-семейства,
  столбец «Порядок»). Итого 449 заданий; внеучебных около 20%, как в реальных запросах (в WildChat учёба — около 70%).
- Рабочие запросы содержат исходные данные (цифры, итоги), как у реального пользователя: иначе модели пришлось бы
  их выдумывать. Творческие и развлекательные задания (мемная презентация, хронология вечера) допускают 0 контрольных
  фактов; в промпте тезисов это нужно разрешить.
- `key_points` обучения **не совпадают с оглавлением одной статьи**, иначе RL поощрял бы копирование её структуры.
  Черновики составляют три LLM разных разработчиков (Claude, GPT, Gemini): темы делятся между ними поровну,
  у каждой темы один черновик. Деление случайное, стратифицированное по `domain` и выборке (train/validation/test),
  чтобы особенности модели не совпали с типом темы. Промпт и формат ответа у всех одинаковые
  (`data/tasks/key_points_prompt.txt`); на входе — id, тема и аудитория. Разделы статей Википедии
  не даём, чтобы тезисы не повторяли их структуру: модель опирается на веб-поиск и свои знания о курсах по теме.
  Обучаемые и сравниваемые модели (T-lite, Qwen) черновики не составляют.
- Условия составления одинаковые у всех трёх моделей: каждая пачка тем — в новом чате, без памяти и истории
  разговоров (весь контекст — в опубликованном промпте); веб-поиск включён, модель перечисляет источники,
  на которые опиралась. Сырые ответы со списками источников сохраняются без правок, вместе с названием модели и датой.
- Точно повторить черновики нельзя (случайная выборка в чате, меняющаяся выдача поиска, обновления моделей в чатах),
  поэтому воспроизводимость обеспечивают опубликованные итоговые списки, промпты и сырые ответы, а не повторная генерация.
- Ответ модели на тему (JSON): тезисы по числу слайдов задания (один тезис на 1–2 содержательных слайда, без титульного
  и заключительного; не больше 10; если число слайдов не задано — сколько нужно для раскрытия темы, не больше 10) —
  `title` (название части темы, как заголовок слайда, до 8 слов),
  `terms` (2–5 ключевых понятий, по которым видно, что тезис раскрыт);
  контрольные факты — обычно 3–8 (при 1–3 слайдах не больше 3; у творческих и бытовых запросов без общепризнанных
  точных сведений — 0) проверяемых утверждений `claim` с коротким конкретным значением `key` — дата, число,
  короткая формула (LaTeX без `$`), имя или название (для оценки точности и испорченных примеров); источники. Аудитория знает базовые понятия своей области: тезисы раскрывают тему
  глубоко, азы отдельными тезисами не выносятся. Роль («ты — преподаватель») в промпте не задаём.
  Не просим: веса, подсказки для поиска, структуру
  презентации, «что за рамками аудитории», пометки неуверенности, типичные ошибки.
- Для каждой темы хранится, какая модель составила черновик. Все черновики проверяются и правятся вручную,
  при необходимости — по учебникам и программам курсов. Итоговые списки фиксируются до обучения.
- LLM-судья на validation/test — модель, которая черновики не составляла, или это оговаривается в работе.
- `key_points` без весов: GRPO сравнивает ответы на одно задание между собой, поэтому общий «потолок»
  покрытия (например, мало слайдов на большую тему) на сравнение не влияет.
- SFT: около 90 полных примеров презентаций в DSL — по 30 от Claude, Codex и Gemini (те же модели, что составляют
  тезисы: перенять их представление о раскрытии темы — желательно). Черновики проверяются и исправляются вручную.
  Примеры: без картинок — 35 из 90, с картинками — 55; все без вызовов поиска и в наборе идут с «Поиск: нет»
  (иначе модель выучит, что при доступном поиске искать не нужно).
  Отдельно — примеры с «Поиск: есть», вызовами `search`/`open`/`read` и `#SOURCE`: их составляем после
  инструментов (пункты 6–7 плана), на реальных результатах поиска, так что каждый id в `#SOURCE` проверяется кодом.
  Порядок: составитель получает запрос и описание инструментов и пишет план и вызовы; вызовы выполняет скрипт
  через те же инструменты, результаты возвращаются составителю, и он пишет презентацию с `#SOURCE` (при необходимости —
  ещё вызовы). Картинки в этих примерах тоже бывают и есть, и нет.
  Если после SFT модель на отложенных темах плохо держит формат, примеры добавляются.
- validation (~25) и test (~60) составляются и проверяются вручную; `key_points` для test не копируются из оглавления статьи.
  Протокол: черновик тем же способом, что и для обучения (те же три модели), плюс обязательная сверка с 2–3 источниками
  (программы курсов и ФГОС, оглавления учебников) → правка → фиксация до обучения; протокол и источники описываются в работе. Источники нужны только для составления
  списка тезисов человеком: модели они не выдаются, хранится только список тезисов.
- Четыре непересекающиеся выборки: SFT (90), train для RL (274), validation (25), test (60); набор — `data/tasks/tasks.json`,
  описание и статистика — `docs/dataset.md`.
  Темы SFT в RL не используются: модель запоминает содержание примеров, и на этих темах роллауты повторяли бы
  запомненный ответ — группа без разброса и завышенная награда. Тезисы составляются только для train, validation и test.
- Разделение по семействам тем: перефразировки одного задания не попадают в разные выборки;
  в test есть семейства тем, которых нет в обучении. Test не используется для настройки.
- Типы тем сбалансированы, деление стратифицировано по `domain`; метрики в отчёте — по типам отдельно.
- Любую тему можно раскрыть по-разному (градиентный спуск — в методах оптимизации и в машинном обучении).
  Эталон тезисов фиксирует одно разумное прочтение — то, которое чаще ожидают от указанной аудитории;
  списков тезисов для разных прочтений не делаем. Смещение случайное (разные темы и составители), а не
  систематическое; покрытие тезисов — лишь часть награды, на validation/test качество оценивает судья.
  В работе это записывается как ограничение.
- Аудитория в заданиях бывает двух видов: с курсом или дисциплиной («студенты старших курсов на занятии по дисциплине
  „Педагогика“») и без них. Курс добавлен к 20% тем из рабочих программ (31, не больше одной на дисциплину); у запросов
  из WildChat — только если его назвал пользователь (15). Всего с курсом 46 заданий (10%); в test — 12 из 60 (20%),
  чтобы метрики по заданиям с курсом можно было показать отдельно. Темы из программ подаются как «тема + аудитория»,
  запросы из WildChat — текстом пользователя (аудитория указана в 37 из 262).
  Пользователю демо рекомендуем указывать курс или дисциплину: тогда прочтение темы совпадает с ожидаемым.

## 7. Награда при обучении

| Компонент | Правило |
|---|---|
| Полнота | покрытие `key_points`: для каждого тезиса — сходство эмбеддингов с ближайшим по смыслу слайдом, затем среднее по тезисам темы; без порога |
| Уместные элементы | бонус за корректный элемент из `expected_elements`, с ограничением сверху |
| Прочие элементы | ноль, без штрафа |
| Ошибки | штраф: формула не рендерится, данные графика не сходятся и т. п. |
| Визуал | бонус за долю слайдов с уместным визуалом (с ограничением); не больше 2 крупных визуальных элементов на слайд, штраф растёт с превышением; формул не больше 3 на слайд |
| Формат | небольшой компонент `parse_rate`; ограничения числа слайдов (только если оно задано в запросе) и слов |
| Избыточность | штраф за повторы без новой информации |
| Инструменты | стоимость каждого вызова инструмента (только при «Поиск: есть») |
| Запреты запроса | штраф за `#IMAGE` при «Картинки: нет» (такой элемент ещё и не считается визуалом) |

- При обучении картинки не скачиваются: оценивается только запрос или описание картинки.
- Покрытие: тезис (`title` и `terms`) сравнивается с каждым слайдом отдельно, берётся лучший слайд; итог — среднее
  по тезисам, поэтому число тезисов в теме на шкалу не влияет. Порога «раскрыт / не раскрыт» нет: GRPO сравнивает
  ответы на одно задание между собой, эталон у них общий, и разный уровень сходства у разных составителей
  на сравнение не влияет. В сравнение идут только видимые элементы слайда: `#TITLE`, `#TEXT`, `#BULLET`, `#QUOTE`,
  подписи `#DIAGRAM`, `#TIMELINE` и `#CHART`. Не идут `#NOTES`, `#IMAGE`, `#SOURCE`, `#PLAN` (иначе модель учится
  прятать содержание туда, где его не видно) и `#FORMULA` (эмбеддер плохо понимает LaTeX; формулы проверяются отдельно).
  Сходство постороннего текста у эмбеддеров не нулевое, поэтому разница между ответами небольшая; если сигнал
  окажется слабым, вычитаем фоновое сходство. Эмбеддер выбираем на первых DSL-роллаутах T-lite.
- Профили нормируются в [0, 1] по заранее зафиксированным шкалам, не по батчу.
- Перед RL награда проверяется на испорченных презентациях (удалённое объяснение, перемешанные слайды,
  неверная дата, выдуманная цитата, лишняя формула, повтор тезиса): награда должна падать.
- Веса компонентов подбираются на train/validation, не на test.

## 8. Метрики и итоговая оценка

- Автоматические метрики разбора, сборки и ограничений считаются на всех ответах.
- LLM-судья — только на validation и test, после сверки с ручной оценкой на небольшой выборке.
- Ручная оценка на test: шкала 0–4 по фактической корректности, глубине, ясности, структуре, визуальному качеству;
  покрытие каждого `key_point` — 0 / 1 / 2. Проверка вслепую, без названий моделей.
- Неизмеренное значение — `null`, а не ноль; рядом со средними публикуются знаменатели.

## 9. Обучение

- SFT: TRL `SFTTrainer` с LoRA на все линейные слои (внимание и MLP), ранг 32–64, скорость обучения примерно в 10 раз
  выше, чем для полного дообучения; loss только по ответу. Основание — «LoRA Without Regret» (Thinking Machines, 2025):
  на небольших наборах SFT и в RL LoRA не уступает полному дообучению, если стоит на всех слоях; LoRA меньше забывает
  исходные знания (Biderman и др., 2024). QLoRA — только при нехватке памяти (Kaggle T4): адаптер, обученный поверх
  4-битной модели, при вливании в 16-битную даёт не ту модель, что обучали, и генерация в 4 битах медленнее.
  Сравнение «полное SFT против LoRA» на тех же 90 примерах — по желанию, если останется время (на 8×V100 помещается).
- Reference для RL: SFT-адаптер сливается с базой во float16 (V100 не поддерживает bfloat16), поверх учится новый LoRA
  (окончательно — на шаге `training/common.py`).
- PPO и GRPO пишем сами на общей основе `training/common.py`; сначала GRPO, затем PPO (критик, GAE).
- Rollout'ы генерируются с температурой 0.9, без top-p/top-k и штрафа за повторы; log-prob в обучении
  считаются при той же температуре. Рекомендованные параметры модели используются только на инференсе.
- Остановка: плато качества на validation по независимой метрике, но не дольше общего предела.
- Сравниваем: исходная модель, только SFT, SFT+PPO, SFT+GRPO — от копий одного SFT-чекпоинта.
- Показываем итоговое качество на test и кривые обучения относительно сгенерированных токенов и времени.
- Эффективность алгоритмов сравниваем только на одном и том же железе; остальные замеры подписываем устройством.

## 10. Модели

- Qwen3-0.6B и Qwen3-1.7B — отладка конвейера.
- Qwen3-4B-Instruct-2507 и T-lite-it-2.1 — кандидаты на основную базу.

## 11. Код и инфраструктура

- Эталонные функции живут только в модулях `src/`; ноутбуки импортируют их для экспериментов и Kaggle.
- Код пишется по одному модулю: модуль + тест + ручная проверка результата.
- Git + приватный репозиторий GitHub — единственный источник кода; Kaggle и сервер берут код оттуда.
- Устройство выбирается автоматически: CUDA → XPU → CPU, с возможностью указать вручную;
  тип чисел — bf16 при поддержке, иначе fp16/fp32.
- Профили запуска: `local` (GTX 1660 Super, 6 ГБ), `server` (университетский, общий: 8×V100 32 ГБ, карты делятся
  между пользователями; диск 50 ГБ, квоту можно расширить), `kaggle` (T4, 16 ГБ).
- На диске сервера храним адаптеры LoRA (десятки МБ), а не слитые модели (по 16 ГБ каждая); веса базовой модели —
  один раз в кэше Hugging Face. Адаптер вливается при загрузке.
- Первый запуск на сервере — пробный прогон T-lite во float16 (`notebooks/tlite_episode_pilot.ipynb`), затем шаг LoRA.
- Правила общего сервера (очереди задач и лимита времени нет): перед запуском — `nvidia-smi` и закрепление свободных
  карт (`CUDA_VISIBLE_DEVICES`); обучение — скриптом в фоне (`tmux` или `nohup`, лог в файл), а не в тетрадке:
  ядро Jupyter и SSH-сессия умирают при обрыве связи; частые чекпоинты с продолжением; обучение работает на одной
  карте, несколько карт только ускоряют; скорость алгоритмов сравниваем в токенах и шагах, время подписываем загрузкой
  сервера; токены доступа — только в переменных окружения; кэш Hugging Face — вне домашней папки, если есть место
  без квоты (`HF_HOME`).
- Метаданные каждого запуска: хеш коммита, версия сохранённых ответов Википедии, устройство, тип чисел, версии библиотек, seed.
- Долгие запуски переживают обрыв связи и возобновляются с чекпоинта
  (LoRA, оптимизатор, scheduler, RNG, позиция в данных, шаг, критик PPO).
